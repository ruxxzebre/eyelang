Examples ​

Each example below is a whole program for a problem most backend developers have met: a reminder before a trial ends, webhooks to a partner who is sometimes down, an uptime check, a morning report, a refund that needs a person's yes. Each shows a different thing Eyelang does for you, and each has tests that pass. The tests run days of waiting in milliseconds, and they answer calls to other services from recorded replies instead of the network.

Open any of them in the playground and press Test to run its tests in your browser. The source of each is in docs/examples.

A few words used below:

  • An entity is a piece of state with one owner, such as one account. Its data changes only through its own methods, each a transaction.
  • A job is a function that can wait for minutes or days. Each step marked ! is saved, so a run that waits is kept on disk, not in memory, and carries on after a restart.
  • A view is a list of entities kept up to date as they change. A job can start when an entity enters or leaves it.
  • A contract describes another service's API: its types and operations. A key on a call lets the service see a repeat and act once.

Trial ending: an email three days before ​

A sign-up gets a 14-day trial and one email three days before it ends, unless they upgrade first. Nothing polls a trial_ends_at column: the job sleeps until the time comes. Because a trial can be extended while the job sleeps, the job reads the account again each time it wakes. An upgrade ends the run, and an extension sends it back to sleep.

eye
## Sleeps until three days before the trial ends, then emails the customer.
## The trial can change while the run sleeps, so it reads the account again
## each time it wakes: an upgrade ends the run, and an extension sends it
## back to sleep.
job remind(id: String) {
  while true {
    let account = Account(id).read!()
    let Trial(ends) = account.plan else { return }
    if now!() >= ends - notice {
      email!(id, account.email)
      return
    }
    sleepUntil!(ends - notice)
  }
}

The tests sign up, move the clock with advance(5 days), upgrade or extend, and check what was sent. Open it in the playground.

Webhook delivery: keys, lost replies and backoff ​

The shop tells a partner about each order event. Three things can go wrong, and each has its answer. An event queued twice is delivered once, because the delivery job starts once per key. A reply lost on the way back is Uncertain, and .reconcile!() asks the partner what happened instead of sending again. A partner that is down is tried again on a schedule the program writes for itself. Eyelang has no retry library: the policy is a list of waits and a short waiting function, and each sleep! in it is a saved step.

eye
## How long to wait after each failed try. The policy is this list: change
## it to change how often, and for how long, the program tries.
let backoff = [1 min, 5 min, 30 min, 2 h, 12 h]

## Whether another try could help: not after a success, and not after an
## answer that says no, such as 410 Gone.
fn worthRetrying(r: Result(a, http.HttpError)) -> Bool = match r {
  Ok(_) => false
  Err(BadStatus(code, _)) => code >= 500
  Err(_) => true
}

## Calls `send`, and calls it again after each wait in `waits` while the
## failure is worth retrying. Each sleep is a durable step, so a restart in
## the middle of a two-hour wait carries on where it was.
fn retry(waits: List(Duration), send: fn() -> Result(a, http.HttpError)) -> Result(a, http.HttpError) uses {wait} {
  var result = send()
  for d in waits {
    if !worthRetrying(result) { return result }
    sleep!(d)
    result = send()
  }
  result
}
eye
## Delivers one event. Every try sends the same key, so the partner acts on
## it once, even when an earlier try got through and only its reply was lost.
job deliver(e: Event) {
  let result = retry!(backoff, fn: endpoint.deliver!(e.kind, e.body, key: "{e.id}").reconcile!())
  let status = match result {
    Ok(ack) => Delivered(receipt: ack.id)
    Err(error) => GaveUp(why: "{error}")
  }
  Outgoing(e.id).finish!(status)
}

The partner's recordings list several replies for one key, which answer the tries in turn: three 503s and then an Ok check that the delivery gets through at 09:36 and not before, and a lost reply, a receipt query that says it never arrived and an Ok check that .reconcile!() sends it again with the same key. Open it in the playground.

Uptime monitor: probe every minute, alert once ​

Every minute each site gets an HTTP GET. Two failures in a row put the site in the view down. The team hears once when a site enters the view and once when it leaves, so there is no "already alerted" flag to keep in step. @concurrency(1) stops a slow round of probes from piling up behind the next.

eye
## Probes every site once a minute. With @concurrency(1), a round that runs
## long makes the next minute's round skip, rather than pile up behind it.
@on(every(1 min))
@concurrency(1)
job probe() {
  for site in Site.all.read!() {
    let found = read(http.get!(site.url))
    Site(site.name).record!(found, now!())
  }
}

## Every site that failed two probes in a row and hasn't answered since.
view down = Site.all |> filter(fn s: s.failures >= 2)

## A site that enters the view has just gone down. The view says when, so
## there is no "alerted" flag to keep: the run starts once per outage.
@on(enters(down))
job wentDown(s: Ref(Site)) {
  let site = s.read!()
  tell!("{site.name} is down: {site.why}", key: "down-{site.name}-{site.outages}")
}

## A site that leaves the view is back.
@on(leaves(down))
job cameBack(s: Ref(Site)) {
  let site = s.read!()
  tell!("{site.name} is back after {site.lastOutage}", key: "up-{site.name}-{site.outages}")
}

The tests fake http.get from recordings of a site that is up and one that answers 503, and check that ten failed probes give one message. Open it in the playground.

Daily report: 08:00 in New York, every weekday ​

At 08:00 New York time on weekdays, the warehouse team hears how many paid orders wait to ship. The schedule names its zone, so the report stays at 08:00 when the clocks change, with no second schedule and no check for summer time. The post's key names the day, so a restart never posts the report twice.

eye
## Posts the report on weekday mornings. The key names the day, so however
## often this step runs, the team sees one report a day.
@on(weekdays(08:00, in: newYork))
job report(day: Date) {
  let at = now!()
  let open = waiting.read!() |> map(fn o: { id: o.id, cents: o.cents, since: o.paidAt ?? at })
  let Some(text) = summary(open, at) else { return }
  match chat.post!("#warehouse", text, key: "report-{day}").reconcile!() {
    Posted(_) => ()
    Refused(_) => log.warn("the chat refused the report for {day}")
  }
}

The test runs from a Friday to the Monday after the clocks go back, and checks that Monday's report comes at 13:00 UTC, an hour later than Friday's. Open it in the playground.

Refund approval: a person says yes first ​

Support asks for a refund, finance has a day to answer, and then the head of finance has a day. The payment provider's refund is @destructive, so it takes an Approval, and only approval!(…) makes one. A refund without a person's yes doesn't compile. Only the person asked can answer, and the run waits on disk for the two days, through restarts.

eye
## Asks finance, and the head of finance if finance doesn't answer within a
## day. Each wait is a durable step: the run sleeps on disk for as long as it
## takes, through restarts, and holds no memory while it does.
fn decide(what: String) -> Decision {
  match approval!(what, from: "finance", within: 1 day) {
    Expired => approval!("{what} (finance didn't answer)", from: "head-of-finance", within: 1 day)
    answered => answered
  }
}

## Reviews one request, refunds it if a person approved, and tells the
## customer.
job review(id: String, r: Request) {
  let status = match decide!("Refund {dollars(r.cents)} on order #{r.order}: {r.reason}") {
    Approved(ok) => refund!(id, r, ok)
    Declined => Refused(why: "declined")
    Expired => Unanswered
  }
  RefundRequest(id).close!(status)
  tell!(id, r, status)
}

## Gives the money back. payments.refund takes the Approval that decide! got;
## without one, this doesn't compile.
fn refund(id: String, r: Request, ok: Approval) -> Status {
  match payments.refund!(r.order, r.cents, approval: ok, key: "refund-{id}").reconcile!() {
    Refunded(refund) => Done(refund:, approvedBy: ok.by)
    NotRefundable(reason) => Refused(why: reason)
  }
}

The tests answer as finance, as someone who wasn't asked, and not at all. Open it in the playground.

Log summary: the plain language ​

Not every program waits. This one reads a web server's access log and prints a table of requests, failures and latency per path. It shows the core language on its own: records and variant types, errors as values with Result and ?, a generic percentile that works on anything that can be ordered, a trait for table rows, and pipes. A line it can't read is reported with its line number, and the rest are still counted.

eye
## Anything a report shows as one row of a table.
trait Row {
  fn cells(self) -> List(String)
}

impl Row for PathStats {
  fn cells(self) = [self.path, "{self.requests}", "{self.failed}", "{self.p50} ms", "{self.p95} ms"]
}

## Pads `s` with spaces to `width` characters.
fn pad(s: String, width: Int) -> String {
  let n = s.chars() |> toList() |> size
  s + ((0..max(width - n, 0)) |> map(fn _: " ") |> join(""))
}

## Lays out rows of any type that is a Row, under a header, in columns.
pub fn table(header: List(String), rows: List(r)) -> String where r: Row {
  let lines = [header] + (rows |> map(fn r: r.cells()))
  let widths = header
    |> enumerate()
    |> map(fn (i, _): lines |> map(fn l: (l[i] ?? "").chars() |> toList() |> size) |> reduce(0, max))
  lines
    |> map(fn l: l |> zip(widths) |> map(fn (cell, w): pad(cell, w)) |> join("  ") |> trim())
    |> join("\n")
}

Press Run in the playground to see the table for a short sample log. Open it in the playground.

A shop and its bank: two programs, one contract ​

The shop charges customers through the bank's Payments contract, and the bank, a second program in bank/, serves it. In the playground, Run starts both and shows each call as it crosses from one to the other. The same order charged twice is paid once, because the key names the order.

eye
## Charges a customer for an order, once however often it runs: the key
## names the order.
job checkout(customer: CustomerId, order: String, cents: Int) uses {entity Order, net Payments.charge, stdio, wait} {
  let charge = payments.charge!(customer, cents, key: "order-{order}").reconcile!()
  let status = match charge {
    Charged(left) => "paid {cents} cents, {left} left"
    Declined(reason) => "declined: {reason}"
  }
  Order(order).settle!(status)
  print("order {order}: {status}")
}

Open it in the playground.
