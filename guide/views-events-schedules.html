Views, events and schedules ​

Jobs don't only start when code calls them. A disk fills up, a message arrives, it's 08:30 on a Monday. The usual ways to react are a cron job that scans a table every minute, a consumer loop on a message queue, and a timer that someone has to keep in step with daylight saving. Each needs its own bookkeeping so that it doesn't miss a change, or act on one twice.

In Eyelang, a job says what starts it with @on(...):

  • enters(view) and leaves(view): an entity starts or stops matching a query.
  • event(contract.event): another service sends an event.
  • daily(...), weekdays(...) and every(...): a schedule on a clock in a time zone.

This page shows each one, and next!, which waits for an event inside a run. It assumes you know entities and jobs.

The code on this page is a real program that the test suite checks and runs. It watches disks: a monitoring service sends readings, a view finds the disks that are nearly full, and jobs page someone and wait for an answer.

Open it in the playground to run it, test it and change it in your browser.

Views ​

Each disk is an entity with its last reading:

eye
entity Disk(host: String) {
  state used: Int = 0

  pub fn report(percent: Int) { used = percent }

  ## Someone has seen the alert: tell every run that waits for it.
  pub fn acknowledge(by: String) uses {publish Monitor.acks} {
    monitor.acks.publish({ host, by })
  }
}

A view is a named query over an entity set, which the runtime keeps up to date as transactions commit:

eye
## Whether a disk is 90% full or more.
fn full(d: Disk) -> Bool = d.used >= 90

## Every disk that is nearly full.
view nearlyFull = Disk.all |> filter(full)

The view starts from Disk.all and filters it with an ordinary function. A view must start from an entity set, since that's what the runtime watches:

text
main.eye:43:1: a view is a pipeline that starts from an entity set, such as World.all

Triggers: enters and leaves ​

@on(enters(view)) starts one run for each entity that begins to match the view, and @on(leaves(view)) one for each entity that stops matching. The job gets a Ref to the entity:

eye
## Pages the on-call person when a disk becomes nearly full, and tells the
## lead if nobody acknowledges it within an hour.
@on(enters(nearlyFull))
job page(d: Ref(Disk)) {
  let host = d.host
  Pager("on-call").add!("{host} is nearly full")
  let ack = next!(monitor.acks, where: fn a: a.host == host, within: 1 h)
  match ack {
    Some(a) => Pager("on-call").add!("{a.by} is on {host}")
    None => Pager("lead").add!("nobody answered for {host}")
  }
}

## Says when a disk is back to normal.
@on(leaves(nearlyFull))
job settle(d: Ref(Disk)) {
  Pager("on-call").add!("{d.host} is fine again")
}

d.host reads the disk's identity, which never changes. To read its state, the job takes a snapshot with d.read!(), as any job does.

A disk that goes from 93% to 95% is still in the view, so it starts nothing new. It is paged once when it fills up, and settled once when it is cleaned:

eye
test "a disk that fills up enters the view, and leaves it when cleaned" {
  monitor.readings.publish({ id: 1, host: "nas", used: 80 })
  expect(Pager("on-call").lines == [])
  monitor.readings.publish({ id: 2, host: "nas", used: 93 })
  monitor.readings.publish({ id: 3, host: "nas", used: 95 })
  expect(Pager("on-call").lines == ["nas is nearly full"])
  Disk("nas").acknowledge("ann")
  monitor.readings.publish({ id: 4, host: "nas", used: 60 })
  expect(Pager("on-call").lines == ["nas is nearly full", "ann is on nas", "nas is fine again"])
}

This replaces a cron job that runs every few minutes, looks for rows over a threshold, and keeps a "paged" flag so it doesn't page twice. The view sees each change as its transaction commits, and starts exactly one run for it.

Events ​

An event is a message another service sends, declared in its contract with a type and a topic:

eye
@auth(bearer: "monitor-token")
contract Monitor {
  ## One reading of one disk. A reading sent twice has the same id.
  @key(id)
  event readings: Reading on "monitor.readings"

  ## Someone has seen the alert for a host.
  event acks: Ack on "monitor.acks"
}

@on(event(monitor.readings)) starts one run for each event, with the event as its argument:

eye
## Each reading the monitor sends starts one run, and updates its disk.
@on(event(monitor.readings))
job record(r: Reading) {
  Disk(r.host).report!(r.used)
}

@key(id) names the field that identifies an event. A message queue may deliver the same message twice; with a key, a repeat starts nothing:

eye
test "a reading sent twice starts one run" {
  monitor.readings.publish({ id: 1, host: "nas", used: 95 })
  monitor.readings.publish({ id: 1, host: "nas", used: 95 })
  expect(Pager("on-call").lines == ["nas is nearly full"])
}

test "nobody acknowledges, so the lead hears about it" {
  monitor.readings.publish({ id: 1, host: "nas", used: 95 })
  advance(1 h)
  expect(Pager("lead").lines == ["nobody answered for nas"])
}

Publishing events ​

A program publishes an event in one of three places:

  • In an entity method. Disk.acknowledge calls monitor.acks.publish(...), and the event is sent when the method's transaction commits. If the transaction rolls back, nothing is sent.

  • In a job, as a durable step, so it's sent once:

    eye
    monitor.acks.publish!({ host, by: "bot" })

  • In a test, to stand in for the other service, as the tests above do. Runs that the event starts or wakes go before publish returns.

Waiting for an event ​

next! waits, inside a run, for the first event that matches. page above waits up to an hour for an acknowledgement of its host:

eye
let ack = next!(monitor.acks, where: fn a: a.host == host, within: 1 h)

It returns Some(event), or None when the hour runs out, and the match after it handles both.

next! misses nothing. It counts every matching event published since the run's previous step, so an answer that arrives while the run is still sending its question, or while it sleeps, is found. Code that subscribes only after it has asked can't lose a fast reply.

Events from other programs ​

Under eye run, the monitoring service sends each event as an HTTP request to the program, with the event as JSON and the secret the contract's @auth names:

text
POST /events/monitor.readings
Authorization: Bearer <secret("monitor-token")>

{ "id": 7, "host": "nas", "used": 93 }

The program takes the events it waits for, with @on(event(…)) or next!, on the port EYE_EVENTS_PORT names (and on the ports of the contracts it serves, if any), and says so when it starts:

sh
MONITOR_TOKEN=… EYE_EVENTS_PORT=8080 eye run .
text
eye run: taking monitor.acks, monitor.readings on :8080

Each event is answered 202 once it is in the journal, then starts its runs and wakes the runs waiting for it. A reading sent again is answered 202 too, and its key starts nothing, so the service may send again whenever it isn't sure. A request without the secret gets 401, and a body that isn't the event's type gets 400. Only the events of a contract with @auth are taken, since without one anyone could publish them. A program that serves a contract sends that contract's events to the programs that take them; see Running in production.

Schedules ​

A schedule starts a run on a clock in a named time zone:

eye
## On weekday mornings, a summary of the disks that are nearly full.
@on(weekdays(08:30, in: dublin))
job morning(day: Date) {
  let hosts = nearlyFull.read!() |> map(fn d: d.host)
  if hosts == [] { return }
  Pager("team").add!("{day.format("%A")}: {hosts |> join(", ")} nearly full")
}

nearlyFull.read!() reads the view as a step: it gives the snapshots of the disks in it, and the run records them, so a run that resumes sees the same disks. In a job, a view, Disk.all or a field of a reference read without a step is an error that says which step to write.

eye
## Compacts the disks every night at 01:30, Irish time.
@on(daily(01:30, in: dublin))
job compact(day: Date) {
  Pager("night").add!("{day} at {now!()}")
}
  • daily(at, in: zone) fires every day at that time on the zone's clock, and weekdays(at, in: zone) Monday to Friday.
  • cron("15 8-18/2 * * mon-fri", in: zone) fires when a crontab line says, on the zone's clock: the five standard fields (minute, hour, day of month, month, day of week) with values, names, ranges, lists and steps. A line that is wrong, or never fires, is an error at the string.
  • every(15 min) fires at each multiple of the interval since midnight UTC: :00, :15, :30, :45.
  • A job that takes a Date gets the date of the firing in the schedule's zone, which makes a good key for anything the run sends.

The zone is part of the schedule, and is checked when the program is compiled:

text
main.eye:105:22: unknown time zone "Europe/Dubln": a zone is named as in the tz database, such as "Europe/Dublin"

A schedule follows its zone through daylight saving. A time that a change skips fires as far after the change as it was meant to be: on the night Dublin's clock jumps from 01:00 to 02:00, 01:30 fires at 02:30. A time that a change repeats fires the first time it comes. So there are never two UTC crons and an hour check. Those are the defaults, and onGap: and onOverlap: choose others: onGap: Skip doesn't fire a skipped time that day, onOverlap: Second fires a repeated time the second time, and onOverlap: Both fires it both times, for a job that should run every hour:

eye
## Rotates the logs on the hour, every hour: on the night the clock goes back,
## the hour it repeats is rotated twice.
@on(cron("0 * * * *", in: dublin, onOverlap: Both))
job rotate() {
  Pager("logs").add!("{now!()}")
}
eye
test "the summary comes on weekday mornings only" {
  with clock(2026-10-16 08:00 in dublin)  # a Friday
  Disk("nas").report(97)
  advance(3 days + 30 min)
  expect(Pager("team").lines == ["Friday: nas nearly full", "Monday: nas nearly full"])
}

test "a time the clock skips runs as far after the change" {
  with clock(2027-03-27 12:00 in dublin)  # at 01:00 on the 28th, the clock jumps to 02:00
  advance(2 days)
  expect(Pager("night").lines == [
    "2027-03-28 at 2027-03-28 02:30 in \"Europe/Dublin\"",
    "2027-03-29 at 2027-03-29 01:30 in \"Europe/Dublin\"",
  ])
}

test "a time the clock repeats runs twice with onOverlap: Both" {
  # 00:30 in Dublin; at 02:00 on summer time, 01:00 UTC, the clock goes back to 01:00
  with clock(2026-10-24 23:30 in "UTC")
  advance(3 h)
  expect(Pager("logs").lines == [
    "2026-10-25 00:00 in \"UTC\"",  # 01:00 on summer time
    "2026-10-25 01:00 in \"UTC\"",  # 01:00 again, on winter time
    "2026-10-25 02:00 in \"UTC\"",
  ])
}

A schedule counts from when the program first starts, and each firing is saved with the run it starts. A restart neither repeats a firing nor skips one: if the program was down when firings were due, the schedule fires once, for the latest. A firing that finds the job's @concurrency limit reached is skipped, not queued (see Limits).

Mistakes this prevents ​

The bugWhy it can't happen
A threshold checked by polling misses a change, or acts on it twiceA view starts one run when an entity enters, as the change commits
A redelivered message is handled twiceAn event's @key starts one run per key
An event is sent for a change that rolled backAn event published in a method goes out when the transaction commits
A reply arrives before the code listens for itnext! counts events since the run's previous step
A schedule runs twice, or not at all, at a daylight-saving changeSchedules run on the zone's clock, with set rules for skipped and repeated times
A firing is lost, or repeated, by a restartEach firing is saved with its run
