Talking to other services ​

A program that charges a card, sends a message or grants access depends on another service, and calls to other services fail in ways that matter. A timeout after the request went out doesn't say whether the card was charged. Retry, and the customer may pay twice. Give up, and the invoice may stay open although the money arrived. Most HTTP clients leave that decision to each place that makes a call, so it is made differently in each place, and usually only after an incident.

A contract describes another service once: its operations, their types, how they go over HTTP, and what to do when a reply is lost. The compiler holds every call to it, and every test of it, to that description.

The code on this page is a real program: invoices that charge a customer's card through a payment service and text them a receipt. Its tests check what this page says:

A contract describes a service ​

A contract lives in a module of its own, a directory, next to the types its operations use:

eye
## What the payment service did with a charge.
pub type Charge =
  ## The money was taken.
  | Charged(id: ChargeId, at: Instant)
  ## The card was declined, and nothing was taken.
  | Declined(reason: String)

## Money given back to a customer, in part or in full.
pub type Refunded = { charge: ChargeId, amountCents: Int }
eye
@http(names: snake)
@auth(bearer: "payments-token")
contract Payments {
  ## Takes money from a customer's card. The service keeps what each key did.
  @http("POST /v1/charges", status: { 201: Charged, 402: Declined })
  @key(required)
  @reconcile(chargeFor)
  command charge(customer: CustomerId, amountCents: Int, description: String) -> Charge

  ## What the charge with this key did, or None if it never arrived.
  @http("GET /v1/charges/by-key/:key")
  query chargeFor(key: Key) -> Option(Charge)

  ## A customer's balance in cents. A failure comes back as an Err instead
  ## of being retried.
  @http("GET /v1/customers/:customer/balance")
  query balance(customer: CustomerId) -> Result(Int, http.HttpError)

  @key(charge)
  event refunded: Refunded on "payments.refunds"
}

A program that imports the module calls the operations as the module's functions: payments.charge!(…), payments.balance(…). The types come from the contract, so a wrong argument or a missing case is a compile error, not a 400 in production.

The ## comments are the service's documentation. They show on hover in your editor and in eye doc, so the people who call the service read the same words as the people who wrote it.

Commands, queries and events ​

Each operation is one of three kinds, and the kind decides what the runtime may do when something goes wrong.

KindWhat it isWhen the service can't be reached
commandChanges something: takes money, sends a messageSent again only if it never went out. A lost reply is Uncertain(key) (below)
queryReads something, and is safe to repeatTried again for about a minute while the run waits, then the run ends as Failed(Unavailable(…))
eventSomething that happened in the other serviceArrives on its own; starts or wakes runs

A query whose caller wants to handle failures itself says so in its result type. balance returns Result(Int, http.HttpError), so a failure comes back as an Err at once, instead of being retried:

eye
## A customer's balance, or a message to show when the service can't say.
pub fn balanceText(c: CustomerId) -> String uses {net Payments.balance} {
  match payments.balance(c) {
    Ok(cents) => "{cents} cents"
    Err(BadStatus(code, _)) => "the payment service answered {code}"
    Err(NoAnswer(_)) | Err(TimedOut) => "the payment service didn't answer"
  }
}
eye
test "a failure the query declares comes back as a value" {
  with fakes(payments, from: "recordings/")
  expect(balanceText(ann) == "the payment service answered 503")
}

An event starts a job with @on(event(…)). @key(charge) names the field that tells one event from another, so a refund that is delivered twice starts one run:

eye
## A refund made in the payment service's dashboard arrives as an event. Its
## @key is the charge, so a refund delivered twice runs this once.
@on(event(payments.refunded))
job refunded(r: payments.Refunded) {
  let paid = Invoice.all.read!() |> find(fn i: i.status == Paid(charge: r.charge))
  let Some(invoice) = paid else { return }
  Invoice(invoice.id).refund!(r.amountCents)
}
eye
test "a refund event marks the invoice refunded" {
  with fakes(payments, sms, from: "recordings/")
  Invoice(InvoiceId("i-1")).issue(ann, 4_250, "+353 85 000 0001")
  payments.refunded.publish({ charge: ChargeId("ch-1"), amountCents: 4_250 })
  expect(Invoice(InvoiceId("i-1")).status == Refunded(amountCents: 4_250))
}

Under eye run, the payments service delivers the event as an HTTP request, with the event as JSON and the contract's @auth secret:

text
POST /events/payments.refunds
Authorization: Bearer <secret("payments-token")>

{ "charge": "ch-1", "amount_cents": 4250 }

This program serves Invoices on port 8080, so it takes the event there too, and says so when it starts (eye run: taking payments.refunded on :8080); a program that serves nothing takes events on EYE_EVENTS_PORT. It answers 202 once the event is in its journal, 401 without the secret, and 400 for a body that isn't a Refunded. Tests publish events with payments.refunded.publish(…). A program publishes the events of a contract it serves from an entity method, a job, or an operation, and eye run sends them to the programs PAYMENTS_EVENTS_URL lists; see Running in production.

Keys make repeats safe ​

@key(required) means every call of the command carries a key, and the service remembers what it did with each key. Asking again with the same key gives the first answer and does nothing twice. Leave the key out and the checker stops you:

text
main.eye:51:33: charge needs an argument for key

Choose the key from your own data, so that the same piece of work always gets the same key. The job below charges invoice-{id}: however often that step runs, after a restart or a lost reply, the card is charged once for each invoice.

eye
## Charges the customer once. The key is the invoice's id, so however often
## this step runs, the payment service takes the money once.
job collect(id: InvoiceId, customer: CustomerId, cents: Int, phone: String) {
  let charge = payments.charge!(customer, cents, "Invoice {id}", key: "invoice-{id}")
    .reconcile!()
  match charge {
    Charged(chargeId, _) => {
      Invoice(id).settle!(Paid(charge: chargeId))
      receipt!(id, phone, "Paid: invoice {id}, {cents / 100}.{cents % 100 |> pad2} EUR.")
    }
    Declined(reason) => Invoice(id).settle!(Unpaid(reason:))
  }
}

A key made from the clock or a random number defeats this, since each retry gets a new key.

When the reply is lost: Uncertain ​

Calls go wrong in two ways, and only one of them is uncertain:

  • Never sent. The connection was refused, or the name didn't resolve. The service can't have done anything, so the request is sent again, command or query.
  • Sent, and the reply was lost. A timeout, a broken connection, or a 5xx answer to a command. The service may or may not have acted. The command's result is Uncertain(key).

The compiler treats Uncertain as one more outcome of every command. Until you deal with it, the result can't be used as the declared type:

text
main.eye:51:33: this command's reply may have been lost, so it may be Uncertain(key): reconcile it with .reconcile!(), or match it with an Uncertain(_) arm

and a match that forgets it isn't exhaustive:

text
main.eye:52:3: this match doesn't handle Uncertain(_): add an arm for it, or `_ => …`

Nor can a command's outcome be dropped. With payments.charge!(…) on a line of its own, whose outcome nothing reads, eye check says:

text
main.eye:51:3: this drops Charge, a command's outcome, which may be Uncertain, so a refusal would go unnoticed: match it, or discard it with let _ = …

For a command whose answer really changes nothing, such as a notice sent on the way to failing anyway, say so with let _ = ….

There are three ways to settle it. The contract picks the way, once, for every caller.

Ask a query. @reconcile(chargeFor) names a query that takes the key and returns an Option of the command's outcome. .reconcile!() asks it: Some is the outcome, and None means the charge never arrived, so it is sent again with the same key. The recording below loses the reply to invoice-i-3, and the test checks that the program asks chargeFor and finds the charge, without charging again:

eye
test "a lost reply is settled by asking chargeFor, not by charging again" {
  with fakes(payments, sms, from: "recordings/")
  let invoice = Invoice(InvoiceId("i-3"))
  invoice.issue(CustomerId("cara"), 1_500, "+353 85 000 0003")
  expect(invoice.status == Paid(charge: ChargeId("ch-3")))
}

Send again. A service that keeps what each key did can answer a repeat without acting twice. Then the command reconciles through itself: @reconcile(issue) on the invoices contract below, or @reconcile(send) on Notify in the approvals tutorial.

Decide yourself. The text message gateway takes no key and can't say what it did. Its command has no @reconcile, so it has no .reconcile!() either. The caller matches Uncertain(_) and decides, here by asking a person to check, because sending again could send a second text:

eye
contract Sms {
  ## Sends a text. Sending it again sends a second text.
  @http("POST /messages")
  command text(to: String, body: String) -> Sent
}
eye
## Texts a receipt. The gateway takes no key, so a lost reply can't be
## settled by asking: a person looks instead, and nothing is sent twice.
fn receipt(id: InvoiceId, phone: String, text: String) {
  match sms.text!(phone, text) {
    Queued(_) | BadNumber => ()
    Uncertain(_) => Invoice(id).unsure!()
  }
}

Calling .reconcile!() on it is a compile error:

text
main.eye:68:9: this command names no @reconcile query, so its Uncertain outcome can't be reconciled: match Uncertain(key) instead

Nothing is ever sent again on a guess. If a query still can't settle a command after three tries, the run stops with a fault rather than guess. A command whose reply was lost is kept in the program's journal until it is settled, so a restart in the middle of reconciling carries on.

When the state may have changed: @fresh ​

A job that reads a service's state, decides, and then acts can act on state that changed in between: it clears a shelf that someone filled again a second ago. @fresh on a command makes every caller say which version of the state it read, and lets the service refuse:

eye
pub type Shelf = { id: String, items: List(String), version: Version }

@port(3004)
contract Shelves {
  query shelf(id: String) -> Shelf

  ## Empties a shelf, unless it changed after `basedOn`.
  @fresh
  command clear(id: String) -> Cleared
}

clear now takes basedOn: Version after its own parameters, and has two more outcomes: Stale, when the shelf changed after that version, and Expired, when the shelf is gone. Neither did anything. The caller handles both, and usually reads again after Stale:

eye
job tidy(id: String) {
  while true {
    let shelf = shelves.shelf!(id)
    match shelves.clear!(id, basedOn: shelf.version) {
      Cleared(n) => {
        Log(id).add!("cleared {n}")
        return
      }
      Stale => ()
      Expired | Uncertain(_) => return
    }
  }
}

Leave out basedOn:, or a Stale or Expired arm, and the checker stops you:

text
main.eye:6:5: this match doesn't handle Expired: add an arm for it, or `_ => …`
main.eye:6:11: clear needs an argument for basedOn: clear is @fresh, so it takes the Version of the state it was based on, as basedOn: snapshot.version

A Version is whatever the service gives: a number or a string. An entity's snapshot has one in its version field, so a program that serves the contract answers from it:

eye
impl shelves.Shelves {
  fn shelf(id) {
    let rack = Rack(id).read()
    { id, items: rack.items, version: rack.version }
  }

  fn clear(id, basedOn) {
    let rack = Rack(id).read()
    if rack.gone { return Expired }
    if rack.version != basedOn { return Stale }
    Cleared(count: Rack(id).empty())
  }
}

Commands that need a person: @destructive ​

@destructive on a command adds a parameter approval: Approval. Only approval! makes an Approval, so the command can be called only after a person said yes:

eye
job demolish(id: String) {
  match approval!("Burn shelf {id}?", from: "operator", within: 1 h) {
    Approved(ok) => {
      let _ = shelves.burn!(id, approval: ok)
    }
    Declined | Expired => ()
  }
}
text
main.eye:17:15: burn needs an argument for approval: burn is @destructive, so it takes the Approval that approval!(…) gives

The shelves program serves and calls both commands, and its tests show each outcome.

Over HTTP ​

Attributes say how each operation goes over HTTP. The address and the credentials are never in the code: they come from the environment when the program runs (see Running in production).

AttributeWhat it does
@http("POST /v1/charges")The method and path. A path segment :name takes the argument of that name
GET and DELETE send the other arguments as query parameters, a list as the parameter repeated; other methods send them as a JSON object
@http(…, status: { 201: Charged, 402: Declined })A reply with that status is read as that variant, from the fields of the body. Any other success is read as the result type
@http(names: snake) on the contractNames are snake_case on the wire: amountCents is amount_cents, and a variant Normal is "normal"
@key(required)The key goes in the Idempotency-Key header. header: "…" names another header, and field: "…" puts the key in the body too
@auth(bearer: "payments-token") on the contractSends Authorization: Bearer and the secret payments-token with every request
@auth(header: "X-Auth-Token", secret: "…")Sends a secret in a header of your choice

Arguments are sent with their defaults filled in. An argument that is None is left out. basedOn and approval go like any other argument (based_on with names: snake).

This is what the payment service received when the program ran against a stand-in, with PAYMENTS_URL and PAYMENTS_TOKEN set:

text
POST /v1/charges
Authorization: Bearer pt-secret
Idempotency-Key: invoice-i-1
Content-Type: application/json
{"amount_cents":4250,"customer":"ann","description":"Invoice i-1"}

How the answer is read depends on its status, and on whether the operation is a command, a query, or a query that returns Result(T, http.HttpError):

The serviceCommandQueryQuery returning http.HttpError
Answers with a status named in status:That variantThat variantOk of that variant
Answers with another 2xxThe body, read as the result typeThe sameOk of the body
Answers with another 4xxA fault that ends the runA faultErr(BadStatus(code, body))
Answers with a 5xxUncertain(key)Tried againErr(BadStatus(code, body))
Answers with 429Tried againTried againErr(BadStatus(code, body))
Can't be reached: the connection is refusedTried againTried againErr(NoAnswer(reason))
Doesn't answer: a timeout or a broken connectionUncertain(key)Tried againErr(TimedOut) or Err(NoAnswer(reason))

"Tried again" means for about a minute, while the run waits; after that the run ends as Failed(Unavailable(…)). A @fresh command reads a 409 as Stale and a 410 as Expired, unless status: names those codes; status: { 412: Stale } names another.

A refused request is a bug in the program or its configuration, not an outcome to handle, so it stops the run where you can see it:

text
main.eye:51:16: job collect: payments.charge was refused with status 404: {"error": "no such route"}

Values as JSON ​

Every value that leaves a program as JSON has one shape: in requests and replies, in recordings, in the schemas model calls use, and in toJson. The test values have one JSON shape checks the examples below.

EyelangJSON
A recordAn object with every field: {"at": "…", "every": 90000, "level": "Busy", "note": null}
A variant of a type whose variants have no fieldsA string: "Busy"
Any other variantAn object tagged with "kind", with its fields: {"kind": "Charged", "id": "ch-1", "at": "…"}
A positional field"value", or "value1", "value2", … when there are several
A type that wraps one value, such as ChargeId("ch-1")That value: "ch-1"
Some(x), Nonex, null
Lists, sets and tuples; a map with string keysArrays; an object
Instant, Date"2026-10-12T09:30:00Z", "2026-10-12"
Duration, SizeA number of milliseconds, a number of bytes
Version, ApprovalA number or a string, as the service gave it; {"what": "…", "by": "…"}
Stale, Expired, Uncertain(key)Always tagged, whatever the command's own variants: {"kind": "Stale"}

So Charged(id: ChargeId("ch-1"), at: 2026-10-12 09:30 in "UTC") goes over the wire as:

json
{ "kind": "Charged", "id": "ch-1", "at": "2026-10-12T09:30:00Z" }

Reading is forgiving in two ways, so a service can grow without breaking its callers: fields a type doesn't declare are ignored, and a missing field of an Option type is None. Anything else that doesn't fit, such as a missing field or a string where a number belongs, stops the run with a fault that names the field.

Implementing the other side ​

In Eyelang, a program serves a contract with impl: one function per operation, named after it, with its parameters in order and the key last for a command with @key. The types and defaults come from the contract, so they aren't written again. Here the invoices program serves its own interface:

eye
@port(8080)
@http(names: snake)
contract Invoices {
  ## Bills a customer. The key names the invoice, so issuing it again with the
  ## same key bills the customer once and gives the same answer.
  @http("POST /v1/invoices")
  @key(required)
  @reconcile(issue)
  command issue(customer: CustomerId, amountCents: Int, phone: String) -> Issue

  ## Where an invoice stands, or None if there is no invoice with this id.
  @http("GET /v1/invoices/:invoice")
  query invoice(invoice: InvoiceId) -> Option(Status)
}
eye
## The program serves its own contract: one function per operation, each run
## as one transaction. The key names the invoice, so a repeated call finds
## the invoice it already made.
impl invoices.Invoices {
  fn issue(customer, amountCents, phone, key) {
    if amountCents <= 0 { return Refused(reason: "an invoice must be for more than 0") }
    let id = InvoiceId("{key}")
    Invoice(id).issue(customer, amountCents, phone)
    Issued(invoice: id)
  }

  fn invoice(invoice) = if Invoice(invoice).customer == None then None else Some(Invoice(invoice).status)
}

Each operation runs as one transaction, as an entity method does: it can't wait, and it may start jobs. The key names the invoice, so a repeated issue finds the invoice it already made, with no separate table of keys:

eye
test "the served contract bills once per key" {
  with fakes(payments, sms, from: "recordings/")
  let first = invoices.issue(ann, 4_250, "+353 85 000 0001", key: "i-1")
  let again = invoices.issue(ann, 4_250, "+353 85 000 0001", key: "i-1")
  expect(first == Issued(invoice: InvoiceId("i-1")))
  expect(again == first)
  expect(invoices.invoice(InvoiceId("i-1")) == Some(Paid(charge: ChargeId("ch-1"))))
  expect(invoices.invoice(InvoiceId("nope")) == None)
  expect(invoices.issue(ann, 0, "+353 85 000 0001", key: "i-9") == Refused(reason: "an invoice must be for more than 0"))
}

A program that serves a contract calls its own implementation, unless the service's URL is set in the environment; then the service is elsewhere.

@port(8080) says where the service listens. A contract that a program serves must have one, and a contract without one, such as the payment service's, is a service outside your network, reached at the URL in its configuration. A contract with a port can also say who may call it: @allow(shop, billing) lets only those modules call its operations, and a call from any other module fails to compile, at the call. The contract's own module, the module that serves it and tests may always call it.

Under eye run, an impl also serves other programs, on the contract's port. A request is read the way an Eyelang caller sends it, so the two sides agree without code of their own:

  • The operation's @http method and path pick it; one without @http is reached only from inside the program. A path nothing answers gets 404, and a known path with another method 405.
  • Its arguments come from the path, the query parameters or the JSON body. One left out takes its default, an Option left out is None, and anything else missing or of the wrong shape gets 400 with { "error": "…" }. A command with @key gets 400 without its key header.
  • With @auth, a request without the secret gets 401 and reaches no code.
  • The reply is the result in the JSON shape above, with the status that status: gives its variant (the lowest, when several do), else 200.
  • A fault answers 500 and changes nothing, so a caller's command comes back Uncertain, and reconciling it sends it again with the same key.

eye run keeps no replies of its own: a repeated key reaches the impl again, which finds what it already did through the entity the key names, as the Invoice named by the key does above.

The playground runs both sides in your browser: a shop that calls a Payments contract, and a bank, a second program in a directory with an eye.toml of its own, that serves it with impl. Run starts the bank first, then the shop, and the shop's calls reach the bank in the page, as the same HTTP requests and replies two eye runs would exchange on real ports, with each request and its status shown as it crosses. An order charged twice with one key is paid once.

In Go or TypeScript, eye gen writes the other side from the contract: the types in the one JSON shape, a client that calls each @http operation, and a server stub that routes requests the way eye run does. eye gen go --module payments . writes a Go package with a PaymentsClient and a PaymentsService interface to implement; eye gen ts --module invoices . writes the same in TypeScript. The output is a build artifact: generate it in the build, don't commit it. See the eye command.

In any other language, a service that an Eyelang program calls needs to do what its contract says:

  • Answer each @http route, reading arguments from the path, the query string or a JSON body.
  • Read and write values in the JSON shape above, with snake_case names if the contract says names: snake.
  • For a command with @key, remember what each key did, and answer a repeated key with the first answer, without acting again.
  • For @reconcile(query), offer that query: the outcome of the command with that key, or null if it never arrived.
  • For a @fresh command, compare basedOn with the current version, and answer 409 without acting when they differ, or 410 when what it acts on is gone.
  • For a @destructive command, record the approval it carries. You can't check it, so let only the callers in @allow reach the service.
  • Answer a bad request with a 4xx, which stops the caller's run, and a passing problem with a 5xx, which a query retries and a command treats as uncertain. Don't answer a command with a 5xx after acting on it, unless a repeat with the same key gives the real answer.

Services without a contract ​

Some services have no contract: a public web page, a status page, a feed. The standard http module reads them:

eye
## Whether the payment service's public status page says all is well. The
## page has no contract, so it is read with http.get.
pub fn serviceUp() -> Bool uses {wait, net, env} {
  let url = env.get!("PAYMENTS_STATUS_URL") ?? "https://status.example.com"
  match http.get!(url, headers: { "Accept": "text/html" }) {
    Ok(page) => looksUp(page)
    Err(_) => false
  }
}

## Reads a status page's answer.
pub fn looksUp(page: http.Response) -> Bool =
  page.status == 200 && page.body |> contains("All systems operational")

http.get! returns Result(http.Response, http.HttpError). Any answer is Ok, whatever its status, with the status, the headers (names in lower case) and the body as text. Err means there was no answer: NoAnswer(reason) or TimedOut. A request that never reached the server, because the connection was refused or the name didn't resolve, is sent again for about a minute, as a query's is; then NoAnswer's reason says why, as "status.example refused the connection, 8 times over a minute". via: is the URL of an HTTP proxy to go through. serviceUp has ! steps, so it runs only in a run, and every outside call in it is a step, the read of PAYMENTS_STATUS_URL included: env.get!(…).

Prefer a contract for any service you call more than once. http.get has the broad effect net rather than net Payments.balance, it has no keys or reconciling, and its answers have no types.

Keep the reading in a pure function, like looksUp, and test it with a Response you build:

eye
test "a status page is read from its status and body" {
  let page: http.Response = { status: 200, headers: {}, body: "<p>All systems operational</p>" }
  expect(looksUp(page))
  expect(!looksUp({ page with status: 503 }))
}

A test that runs the call itself answers it from a recording, as for a contract: with fakes(http, from: "recordings/") reads recordings/http.json, whose exchanges are keyed by URL. An exchange without a key answers any other URL, and a URL that nothing answers fails the test:

json
{ "contract": "http",
  "exchanges": [
    { "op": "get", "key": "https://status.example.com",
      "result": { "kind": "Ok", "value": { "status": 200, "headers": {}, "body": "All systems operational" } } },
    { "op": "get",
      "result": { "kind": "Err", "value": { "kind": "NoAnswer", "reason": "refused" } } }
  ] }

Testing with recordings ​

Tests don't call real services. with fakes(…) answers each call from a recording of a real answer, one JSON file per contract module, named after the module:

json
{
  "contract": "Payments",
  "exchanges": [
    {
      "op": "charge",
      "key": "invoice-i-1",
      "result": { "kind": "Charged", "id": "ch-1", "at": "2026-10-12T09:30:00Z" }
    },
    {
      "op": "charge",
      "key": "invoice-i-2",
      "result": { "kind": "Declined", "reason": "insufficient funds" }
    },
    { "op": "charge", "key": "invoice-i-3", "result": { "kind": "Uncertain", "key": "invoice-i-3" } },

  • An exchange is found by its operation and, for a call with a key, the key. A call without a key gets the first exchange for its operation.
  • Each result is in the JSON shape above, and is checked against the contract when the fakes are applied, so a recording that no longer fits the contract fails the test that uses it.
  • A lost reply is recorded as { "kind": "Uncertain", "key": "…" }. That is how the test of invoice-i-3 loses a reply on purpose.
  • Keep other scenarios in other directories. The test of a lost text uses with fakes(sms, from: "recordings/lost-text/") and the usual payment recordings.

A call that no recording answers stops the run, and the test fails with the operation and key it was looking for.

WARNING

A test without fakes for a contract calls the real service if its URL variable, such as PAYMENTS_URL, is set in the environment. Give every test that reaches another service its fakes.

See Testing with time and recordings for clocks, events and approvals in tests.

What this rules out ​

  • Charging twice. A command is never sent again on a guess. A lost reply is settled by asking, or by a repeat that the key makes harmless, or by a person.
  • Ignoring a lost reply. Uncertain is part of every command's result type, and match must handle it.
  • Acting on state that changed. A @fresh command names the version it was based on, and the caller must handle Stale and Expired.
  • Destroying without a person. A @destructive command needs an Approval, which only approval! makes.
  • Credentials in code. Addresses and secrets come from the environment; the contract names only the secret.
  • Drift between caller and service. The types, routes and keys are written once, and recordings are checked against them.
