Entities ​

Most programs that run for days keep some shared state: a team's credit, a request's status, a disk's last reading. Several callers change it, and some of them run at the same time. The usual tools are a database row and a lock, or an object that many parts of the program hold, and the usual bugs are lost updates, half-done changes and reads of state that has already moved on.

In Eyelang, shared state lives in an entity. An entity has an identity, state that only its own methods can change, and methods that each run as one transaction. This page explains how to use entities well, and which mistakes they rule out. It assumes you have read An entity in the tutorial.

The code on this page is a real program that the test suite checks and runs.

Open it in the playground to run it, test it and change it in your browser.

An identity and its state ​

A wallet holds a team's prepaid credit for model calls:

eye
type SpendError = | Short(balance: Int)

## A team's prepaid credit, in cents.
entity Wallet(team: String) {
  state cents: Int = 0
  state spent: Int = 0
  state warned: Bool = false

  pub fn topUp(n: Int) {
    cents += n
    warned = false
  }

  pub fn spend(n: Int) -> Result((), SpendError) {
    if n > cents { return Err(Short(balance: cents)) }
    cents -= n
    spent += n
    Ok(())
  }
}
  • entity Wallet(team: String) declares the entity and its identity. Wallet("ops") and Wallet("research") are two wallets.
  • Each state field has a default, which a new wallet starts with.
  • A pub fn is a method that other code can call. Inside it, the state fields are variables.

Wallet("ops") names a wallet; it doesn't create one. An entity exists from its first use, with its defaults, so there is no "create" step and no "not found" case to handle:

eye
test "the identity is the entity" {
  Wallet("ops").topUp(200)
  expect(Wallet("ops").cents == 200)
  expect(Wallet("research").cents == 0)  # exists from its first use
}

The identity is fixed. A method that assigns to it doesn't compile:

text
main.eye:4:30: team is the entity's identity and can't change

If something about an entity can change, such as a team's display name, make it a state field.

Each method call is one transaction ​

A method runs with one writer at a time per entity, and all of it commits or none of it does. Nothing outside the method sees a change until the call returns.

eye
test "a wallet keeps its state between calls" {
  let ops = Wallet("ops")
  ops.topUp(1000)
  expect(ops.spend(300) == Ok(()))
  expect(ops.spend(800) == Err(Short(balance: 700)))
  expect(ops.cents == 700 && ops.spent == 300)
}

So spend can check the balance and then take from it, and no other caller can spend the same cents in between. You don't write a lock, and you can't forget one: the only way to change a wallet's state is to call one of its methods.

Put the check and the change in the same method. Code that reads ops.cents outside, decides, and then calls a method that sets a new value has the same race as any read-then-write: two callers can read the same balance. A method that does both can't.

Calls to other entities commit together ​

A method can call methods of other entities. The whole call tree is one transaction:

eye
## Moves credit from one team to another. Both wallets change in one
## transaction, or neither does.
entity Ledger(name: String) {
  state moves: Int = 0

  pub fn move(from: Ref(Wallet), to: Ref(Wallet), n: Int) -> Result((), SpendError) uses {entity Wallet} {
    from.spend(n)?
    to.topUp(n)
    moves += 1
    Ok(())
  }
}
eye
test "nested calls commit together" {
  let ops = Wallet("ops")
  let research = Wallet("research")
  ops.topUp(1000)
  expect(Ledger("main").move(ops, research, 400) == Ok(()))
  expect(ops.cents == 600 && research.cents == 400)
  expect(Ledger("main").move(research, ops, 900) == Err(Short(balance: 400)))
  expect(Ledger("main").moves == 1)
}

from.spend(n)? and to.topUp(n) change two wallets, and moves += 1 changes the ledger. Either all three commit, or, if the call stops on a fault, none of them does. A reader never sees credit that has left one wallet and not yet reached the other.

An Err is a value, not a rollback

Returning Err from a method doesn't undo what it changed: the method ends normally, and its changes commit. Only a fault, such as unreachable, rolls a transaction back. So check first and change after, as spend does: it returns Short before it touches cents, and move calls spend before topUp.

A call can also come back to an entity whose method is still running: the ledger's move calls a wallet, and the wallet calls the ledger. That is still one transaction, and the ledger has one state in it. The call that comes back starts from what move has changed so far, move goes on from what that call changed, and the ledger commits once with both. A value move read before the call, such as let before = moves, keeps what it read.

Methods stay inside the program ​

A method holds its entity while it runs, so it can't pause. It can't sleep, wait for an event or call another service. A method with sleep! in it doesn't compile:

text
main.eye:109:7: an entity method is a transaction and can't wait; start a job for this instead

The runtime may run a method again after a conflict, so a method does nothing that someone outside the program would see twice. It can't call another service, read or write files, run programs, read the clock, the environment or a secret, draw random numbers or call foreign code, itself or through a function it calls:

text
main.eye:12:13: now uses clock, which an entity method can't: it runs as a transaction, which may run again after a conflict, so what reaches outside the program or waits belongs in a job, which the method can start

What it may do commits with the transaction: change its state, call other entities' methods, start jobs and publish events. Printing and logging are allowed too, since a line written twice on a retry harms no one. A method that needs the time takes it as an argument. Work that waits or reaches outside belongs in a job, which the method can start.

References ​

Ref(Wallet) is the type of a reference to a wallet. A reference is an identity, not a pointer: you can keep it in a record or a list, pass it to a job, and save it, and it always names the same wallet. move takes two of them. Calling a method through a reference, from.spend(n), is the same as calling it on Wallet(...), and from.team reads the identity.

Snapshots ​

read() returns a snapshot: the entity's identity, its state and a version that counts the transactions that changed it, from 0 for a new entity. The snapshot's type has the entity's name, so a function can take one:

eye
## What a team sees on its dashboard. It takes a snapshot, a plain value, so
## it can't change the wallet.
fn describe(w: Wallet) -> String {
  let left = "{w.team}: {w.cents} cents left"
  if w.spent == 0 { left } else { "{left}, {w.spent} spent" }
}
eye
test "a snapshot doesn't change when the entity does" {
  let ops = Wallet("ops")
  ops.topUp(500)
  let before = ops.read()
  let _ = ops.spend(200)
  expect(before.cents == 500 && before.version == 1)
  expect(ops.read().version == 2)
  expect(describe(before) == "ops: 500 cents left")
  expect(describe(ops.read()) == "ops: 300 cents left, 200 spent")
}

A snapshot is a plain value. It doesn't change when the entity does, and changing a copy of it doesn't change the entity. Pass snapshots to code that should look but not touch: describe is a private function here, and it can't change a wallet because it never gets one.

In a job, read!() takes a snapshot as a durable step. A snapshot goes stale as soon as the next transaction commits, so a job that waits reads the entity again after the wait instead of trusting what it read before. Outside jobs, w.cents is short for w.read().cents; in a job it is an error, since a resumed run would read the wallet again and could see another value: read a snapshot with w.read!() and take the field from it.

Wallet.all is every wallet, as a collection of snapshots, so the usual pipes work on it:

eye
test "Wallet.all is every wallet" {
  Wallet("ops").topUp(50)
  Wallet("research").topUp(5000)
  let low = Wallet.all |> filter(fn w: w.cents < 100) |> map(fn w: w.team)
  expect(low == ["ops"])
}

A job reads it as a step, Wallet.all.read!(), which records the list.

Starting a job from a method ​

A method can't wait, but it can start a job that does. The start is part of the transaction: the run begins only if the method commits. Starting a job is an effect, so a public method that starts one says so in its signature, uses {start warnLow}.

eye
## Like Wallet, but it warns the team once when it runs low.
entity Quota(team: String) {
  state cents: Int = 0
  state warned: Bool = false

  pub fn topUp(n: Int) {
    cents += n
    warned = false
  }

  pub fn spend(n: Int) -> Result((), SpendError) uses {start warnLow} {
    if n > cents { return Err(Short(balance: cents)) }
    cents -= n
    if cents < 100 && !warned {
      warned = true
      warnLow.start(team)
    }
    Ok(())
  }
}

job warnLow(team: String) {
  let q = Quota(team).read!()
  Outbox(team).add!("only {q.cents} cents left")
}

## The messages a team was sent. A real program would send them with a
## contract; this one keeps them so the tests can look.
entity Outbox(team: String) {
  state sent: List(String) = []

  pub fn add(text: String) { sent += [text] }
}
eye
test "a method starts a job when it commits" {
  let q = Quota("ops")
  q.topUp(500)
  let _ = q.spend(450)
  let _ = q.spend(20)
  expect(Outbox("ops").sent == ["only 50 cents left"])
}

The second spend takes the quota below 100 cents and starts warnLow. warned and the started run commit together, so the team is warned exactly once: a call that rolls back starts nothing, and a call that commits can't lose its warning.

With a database and a queue, this is two writes to two systems, and a crash between them leaves a change without its follow-up, or a follow-up for a change that never happened. The usual fix is an outbox table and a relay process. Here the transaction covers both.

start also takes after: (start later), at: (start at a time) and key: (start once per key). See Jobs and waiting.

Ending an entity ​

An entity lasts until one of its own methods calls end(ok). ok is an Approval, which only approval! gives, so deleting an entity's data always takes a person's consent. The approval comes from a job, which passes it to the method:

eye
## A team's access to the models. Closing it deletes its data, so it needs
## a person's approval.
entity Team(name: String) {
  state members: List(String) = []

  pub fn join(who: String) { members += [who] }

  pub fn close(ok: Approval) { end(ok) }
}

job closeTeam(name: String) {
  let decision = approval!("Close team {name}?", from: "finance", within: 2 days)
  let Approved(ok) = decision else { return }
  Team(name).close!(ok)
}
eye
test "a team ends once finance approves" {
  Team("ops").join("ann")
  closeTeam.start("ops")
  approve("Close team ops?")
  expect(Team.all |> size == 0)
}

When the transaction commits, the entity's state is removed: Team.all no longer lists it, and it leaves every view, so jobs on leaves(…) start. The store keeps only that it ended, when, and whose approval let it. A reference to it is still a value whose identity you can read, but calling it or reading it stops the run with a fault, and the identity never starts again, so a job holding an old reference can't bring the team back by mistake:

text
Team("ops") ended at 2026-10-12 09:00 UTC, approved by finance ("Close team ops?"), so it can't be read or changed

end without an Approval doesn't compile, and neither does calling it on another entity. Inside an entity's method, end is the entity's; elsewhere it is a string's end, s.end().

text
main.eye:9:7: ending an entity needs an Approval: end(ok), with ok from approval!(…) in the job that calls this method

Changing the shape of stored state ​

Entities outlive the code that wrote them, so their state has a shape version. @version(N) numbers the shape (1 without it), and every stored row records the version it was saved at.

eye
## Version 1 kept whole credits as `credits`; version 2 keeps cents.
@version(2)
entity Account(team: String) {
  state cents: Int = 0
  ## Added later with a default: needs no new version.
  state frozen: Bool = false

  pub fn add(n: Int) { cents += n }

  migrate from 1 (old) {
    { cents: old.credits * 100 }
  }
}
  • Adding a field with a default needs no new version. A row without the field gets the default when it is loaded. frozen was added this way.
  • Any other change, such as a rename or a new field without a default, raises @version by one and adds migrate from the old version: a pure function from the row as it was stored to the state at the next version. old is that row. Its fields are read by name, and checked when the migration runs.
  • Migrations chain. A row saved at version 1 of a version-3 entity runs migrate from 1, then migrate from 2, when it is loaded. So an entity needs a migration from each version between its oldest rows and the current one.

The checker holds you to the chain:

text
main.eye:1:1: Account is at @version(3), so it needs migrate from 2: adding a field with a default needs no new version, and any other change needs a migration from the old one

and to the result, which must give every field without a default a value:

text
main.eye:7:5: this Account state has no owner: every field needs a value

Here is the change above on a real journal, from a copy of the program whose main prints the account's snapshot. Before the change, main added 3 credits. After it, the stored row loads as 300 cents, with frozen at its default, and main adds 50 more. The version in each snapshot is the transaction count (1, then 2), not the shape version:

text
{ team: "ops", version: 1, credits: 3 }
{ team: "ops", version: 1, cents: 300, frozen: false }
{ team: "ops", version: 2, cents: 350, frozen: false }

eye run reads every stored row's version before it starts. If a migration is missing, it refuses to start, rather than load state it can't read:

text
eye run: stored entities can't reach this program's versions: 1 Account saved at version 1, and Account has no migrate from 1

When to use an entity ​

Use an entity for state that outlives a call and has more than one writer: a balance, a request moving through its steps, the last reading of a disk. Its methods are the only way to change it, and each change is a transaction.

Use a plain value for everything else: a price list, a request's details, a parsed message, the result of a calculation. Values are immutable, cost nothing to share, and are passed by value, so nothing changes behind your back. When code only needs to look at an entity, give it a snapshot.

A few signs that something should be an entity:

  • Two parts of the program, or two runs of a job, change it.
  • It must survive a restart.
  • A job needs to wait for it to change, which a view can notice.

Mistakes this prevents ​

The bugWhy it can't happen
A lost update: two callers read, both writeA method checks and changes in one transaction, one writer at a time
Half a change is visibleNothing outside a method sees its changes until it commits, nested calls included
A change commits, its follow-up is lostA job started in a method begins only if the method commits
A lock held across a network callMethods can't wait, so they finish quickly
A retried transaction sends a message twiceMethods can't call services or touch files; the jobs they start begin once, when they commit
"Not found", or two rows for one thingAn entity exists from its first use, and its identity can't change
Old rows that the new code can't read@version and migrate from are checked, and eye run refuses rows it can't migrate
