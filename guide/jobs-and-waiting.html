Jobs and waiting ​

A program that keeps state spends most of its time waiting: for a reminder's time, for a person to answer, for a slow export, for tomorrow morning. The usual ways to wait are a sleeping thread, which is lost on a restart, or a table of pending work with a status column, a worker that polls it, and a cron job that cleans up after both.

In Eyelang, waiting is done by jobs. A job is a function that can pause for as long as it needs. While it waits it holds no thread and no memory, only a saved record, and it carries on after a restart from where it was. This page explains what is saved, how runs start and are limited, and how they end. It assumes you have read A job that waits in the tutorial.

The code on this page is a real program that the test suite checks and runs.

Open it in the playground to run it, test it and change it in your browser.

A job is a durable function ​

A reminder rings at its time, unless it is snoozed first:

eye
entity Reminder(id: String) {
  state text: String = ""
  state due: Instant = 2026-01-01 00:00 in "UTC"

  pub fn set(t: String, at: Instant) uses {start ring} {
    text = t
    due = at
    ring.start(id, key: "ring-{id}")
  }

  pub fn snooze(by: Duration) { due = due + by }
}
eye
## Rings a reminder when it is due. A snooze moves the time while the run
## sleeps, so it reads the reminder again after every wait.
job ring(id: String) {
  var me = Reminder(id).read!()
  while me.due > now!() {
    sleepUntil!(me.due)
    me = Reminder(id).read!()
  }
  Log("rang").add!("{me.text} at {now!().time(in: "Europe/Dublin")}")
}

job ring reads like an ordinary function. The difference is the calls marked with !. Each one is a durable step: a call that waits, reads the clock, touches an entity or calls another service. Calls without ! only compute.

ring reads the reminder, sleeps until it is due, and reads it again. If someone snoozed it in the meantime, due has moved, and the loop sleeps again. A job that waits should read state again after the wait, because whatever it read before is a snapshot from before the wait.

eye
test "a reminder rings at its time, and a snooze moves it" {
  with clock(2026-10-12 09:00 in "Europe/Dublin")
  Reminder("tea").set("put the kettle on", 2026-10-12 10:00 in "Europe/Dublin")
  Reminder("call").set("call the plumber", 2026-10-12 11:00 in "Europe/Dublin")
  advance(1 h)
  expect(Log("rang").lines == ["put the kettle on at 10:00"])
  Reminder("call").snooze(30 min)
  advance(2 h)
  expect(Log("rang").lines == ["put the kettle on at 10:00", "call the plumber at 11:30"])
}

What is saved at a ! ​

At each !, the run saves its live variables and records the call's result. When the run resumes, after a sleep or after a restart, it goes on from the last step, with the same values. It never makes a recorded call again: an entity call that committed isn't repeated, a message that was sent isn't sent twice, and now!() returns the time it returned the first time.

You can see this with eye run. The program's main sets a reminder for one minute from now, the first time it runs:

eye
## Sets one reminder the first time the program starts.
pub fn main() uses {clock, entity Reminder, start ring} {
  let r = Reminder("stretch")
  if r.read().version == 0 {
    r.set("stand up and stretch", now() + 1 min)
  }
}

Start it with eye run, stop it with Ctrl-C while the reminder waits, and look at the journal with eye runs:

text
.eye/journal: 2.5 KiB on disk, 795 B live, 6.9 GiB free; 1 runs, 1 not finished
#1 ring("stretch")  sleeping until 2026-10-11 02:11:23 (in 56s)  [3 steps, 437 B]
    1. Reminder(stretch).read → { id: "stretch", version: 1, text: "stand up and stretch", due: 2026-10-11 02:11 in "Local" }
    2. now → 2026-10-11 02:10 in "Local"
    3. sleepUntil, sleeping until 2026-10-11 02:11:23 (in 56s)

The waiting run is 437 bytes in the journal: its arguments, its live variables and three recorded steps. Start the program again, and main sees the reminder exists and does nothing, while the run sleeps on. When its time comes it finishes, and eye run exits because nothing is left to wait for:

text
#1 ring("stretch")  done  [7 steps, 760 B]
    1. Reminder(stretch).read → { id: "stretch", version: 1, text: "stand up and stretch", due: 2026-10-11 02:11 in "Local" }
    2. now → 2026-10-11 02:10 in "Local"
    3. sleepUntil, slept until 2026-10-11 02:11:23
    4. Reminder(stretch).read → { id: "stretch", version: 1, text: "stand up and stretch", due: 2026-10-11 02:11 in "Local" }
    5. now → 2026-10-11 02:11 in "Local"
    6. now → 2026-10-11 02:11 in "Local"
    7. Log(rang).add

Steps 5 and 6 are the two now!() calls: the loop's test, and the time in the message. If the program had stopped after step 7 was recorded, a restart would not add the line again. A run that was due while the program was down runs as soon as it starts.

An entity call from a job commits in the same transaction as the step that records it, so it happens exactly once. The checker makes sure every such call is marked:

text
main.eye:34:10: in a job, an entity call is a durable step: write read!(…)

Only values that can be saved ​

A value that is live across a ! is saved with the run, so it must be a value that can be saved. A Secret can't, so holding one across a wait is an error, in a job or in a waiting function it calls, where a parameter counts as well. A function is saved as its code and what it captured, so a lambda that captures only what can be saved may be held across a wait:

text
main.eye:4:14: token is a Secret, which can't be saved, and it is still needed after a waiting call: read the secret in a function that uses it and returns what can be saved, and call that with !

Ways to wait ​

Every waiting call is a library function, called with !:

CallWaits for
sleep!(20 min), sleepUntil!(at)a time
approval!(text, from:, within:)a person to approve or decline
next!(event, where:, within:)an event; see Views, events and schedules
poll!(every:, within:, check)a service that can't say when it is ready
run.join!()a run started earlier; see Outcomes and faults
allDone!(runs), firstDone!(runs)every one, or the first, of several runs; see Concurrency inside a job
lock!(name, for:, f)a named lock no other run holds; see Concurrency inside a job

A wait that can last long takes a within:, and says what happens when time runs out. Here a clean-up asks a person before it deletes anything:

eye
## Deletes old backups, but only if a person says yes within a day.
job prune(old: Int) {
  match approval!("delete {old} old backups", from: "operator", within: 1 day) {
    Approved(ok) => Log("backups").add!("deleted {old}, approved by {ok.by}")
    Declined => Log("backups").add!("kept {old}: declined")
    Expired => Log("backups").add!("kept {old}: nobody answered")
  }
}

approval! returns a Decision, and the match must handle all three: Approved, Declined and Expired. A day with no answer is a case the code decides on, not an exception or a run that waits forever. Approved holds an Approval, whose what and by say what was approved and by whom, for a log.

Only the person in from: may answer: an answer from anyone else is refused and logged, and the run keeps waiting. In tests, approve(...) and decline(...) answer the one request whose text contains what they are given, as the person asked unless by: says otherwise. They fail the test when no request's text, or more than one, contains it:

eye
test "a person approves the clean-up" {
  prune.start(3)
  expect(Log("backups").lines == [])
  approve("delete 3 old backups", by: "someone else")
  expect(Log("backups").lines == [])  # only the person asked may answer
  approve("delete 3 old backups")
  expect(Log("backups").lines == ["deleted 3, approved by operator"])
}

test "nobody answers, so nothing is deleted" {
  prune.start(3)
  advance(1 day)
  expect(Log("backups").lines == ["kept 3: nobody answered"])
}

Outside tests, a request reaches a person through the program. When a run starts waiting, the runtime publishes approvals.requested, with the request's id, what, from and until. A job of the program asks the person, and publishes their answer as approvals.answered, naming the request by its id:

eye
import approvals

@on(event(approvals.requested))
job ask(r: approvals.Request) {
  let left = r.until - now!()
  let asked = notify.ask!(to: operator, text: r.what, choices: [yes, no], within: left,
    key: "approval-{r.id}").reconcile!()
  let Asking(question) = asked else { return }
  let Some(press) = next!(notify.answered, where: fn a: a.question == question, within: left) else {
    return
  }
  approvals.answered.publish!({ id: r.id, approved: press.choice == yes.id, by: "{press.by}" })
}

The job doesn't check who pressed the button: the runtime compares by with the request's from, both as text, and refuses an answer from anyone else. And since the answer names its request, two runs that ask the same thing are answered one by one. The check guards against a press by the wrong person; it can't tell a real press from code that writes by: r.from itself, so publish approvals.answered only from the job that hears the person.

A person can also answer from a shell where the program runs: eye approve and eye decline answer a run of eye run in that directory, as in eye approve . "delete 3 backups". When more than one waiting approval contains the text, they answer none and list the approvals with their ids; eye approve --id ID . answers one. eye runs shows what each run waits for, its id, and until when. A run waiting for an approval survives a restart of eye run, with the same deadline and id.

poll! is for services that can only be asked:

eye
let ready = poll!(every: 1 min, within: 6 h, fn { feed.ready!() })

It calls the check every minute until it returns true, and gives false if six hours pass first. Only its outcome is kept, so a long poll doesn't grow the run's history.

Starting runs ​

A run starts in one of four ways:

  • From an entity method, as part of its transaction. set starts ring, and the run begins only if set commits. See Entities.
  • From a job, as a child run: export.start!(t) below. The start is a durable step, so a resumed run doesn't start the child again.
  • From main or a test. In a test, the run goes as soon as the call returns, until it finishes or waits.
  • From a trigger: @on(...) starts a run on a schedule, when an entity enters or leaves a view, or when an event arrives. See Views, events and schedules.

start returns a Run, and takes three optional arguments:

eye
ring.start(id, after: 20 min)
  • after: starts the run later, and at: at a given instant.
  • key: starts a job once per key. A later start with the same key returns the first run, finished or not, and starts nothing.

set gives its run a key, so setting a reminder twice rings it once. Since ring reads the reminder when it wakes, it rings with the latest text and time:

eye
test "setting a reminder twice starts one run" {
  with clock(2026-10-12 09:00 in "Europe/Dublin")
  let r = Reminder("tea")
  r.set("put the kettle on", 2026-10-12 10:00 in "Europe/Dublin")
  r.set("put the kettle on, now", 2026-10-12 10:15 in "Europe/Dublin")
  advance(1 day)
  expect(Log("rang").lines == ["put the kettle on, now at 10:15"])
}

main runs every time the program starts, so a job it starts must have a key. Without one, the checker refuses the call:

text
main.eye:6:3: eye run runs main every time it starts, so this would start ping again after each restart; give the run a key, which starts it once: ping.start(…, key: "…")

Limits ​

Attributes on a job tell the runtime how many runs may go at once, how often they may begin, and how long they may take:

eye
## Posts to a chat. The chat service allows one message a second in each
## chat, and the runtime keeps to that.
@limit(1, per: 1 s, by: chat)
job post(chat: String, text: String) {
  Log(chat).add!(text)
}

## Rebuilds a chat's search index, one rebuild at a time per chat.
@concurrency(1, by: chat)
job reindex(chat: String) {
  Log("reindex").add!("start {chat}")
  sleep!(10 min)
  Log("reindex").add!("end {chat}")
}
  • @limit(n, per: duration, by: param) lets at most n runs begin in any window of that length. A run over the rate waits until the window lets it begin. Use it for another service's rate limit.
  • @concurrency(n, by: param) lets at most n runs go at once. A run over the limit waits in a queue and begins when one finishes, in the order they were started. Use it when runs must not overlap, such as one question at a time to the same person.
  • by: names a parameter, and applies the limit to each of its values on its own: chats don't wait for each other.
eye
test "@limit spaces runs out, per chat" {
  post.start("team", "one")
  post.start("team", "two")
  post.start("family", "hello")
  expect(Log("team").lines == ["one"] && Log("family").lines == ["hello"])
  advance(1 s)
  expect(Log("team").lines == ["one", "two"])
}

test "@concurrency queues runs, per chat" {
  reindex.start("team")
  reindex.start("team")
  reindex.start("family")
  advance(10 min)
  expect(Log("reindex").lines == ["start team", "start family", "end team", "start team", "end family"])
}

A scheduled firing that finds a @concurrency limit reached is skipped, not queued, so a slow run of a job that fires every minute doesn't build a backlog.

Outcomes and faults ​

A run ends with an Outcome: Completed(value), with what the job returned, or Failed(fault) when it stopped first. A Fault is not an error the job returns. It is something that stopped the run from outside its logic, such as DeadlinePassed from @deadline, or Unreachable when the code reached unreachable(...). Code can't catch a fault where it happens. To report one, start the work as a child run and join it:

eye
type Table = { name: String, minutes: Int }

## Exports one table. The sleep stands in for slow work in another service.
@deadline(30 min)
job export(t: Table) -> Int {
  sleep!(1 min * t.minutes)
  t.minutes * 1000
}

## Starts one export per table, then waits for each. The exports run at
## once; one that passes its deadline is reported, not lost.
job nightly(tables: List(Table)) {
  var runs = []
  for t in tables { runs += [(t.name, export.start!(t))] }
  for (name, run) in runs {
    match run.join!() {
      Completed(rows) => Log("nightly").add!("{name}: {rows} rows")
      Failed(fault) => Log("nightly").add!("{name}: {fault}")
    }
  }
}

@deadline(30 min) ends a run that is still going 30 minutes after it started, even while it sleeps. nightly starts all three exports before it waits for any, so they run at the same time, and the whole night takes as long as the slowest one:

eye
test "child runs go at once, and a fault comes back as an outcome" {
  let start = now()
  nightly.start([{ name: "users", minutes: 5 }, { name: "events", minutes: 45 }, { name: "logins", minutes: 20 }])
  advance(1 h)
  expect(Log("nightly").lines == ["users: 5000 rows", "events: DeadlinePassed", "logins: 20000 rows"])
  expect(now() - start == 1 h)
}

@deadline also takes a time of day: @deadline(13:40, in: "Europe/Dublin").

Only a job waits for a run. A test or main reads where a run got to with run.outcome(): None while it is still going, and Some(Completed(value)) or Some(Failed(fault)) once it has ended. See Testing.

Errors that the job can handle belong in its return type, as a Result. Faults are for what it can't: a deadline, a bug, a service that stayed down.

Concurrency inside a job ​

Child runs are how a job does durable work at the same time, as nightly does. The task functions parallelMap, both, race and timeout work in a job only for work that computes, because a task's steps can't be recorded. A task that takes a ! step stops the run:

text
main.eye:8:26: job inBoth: a task in a job can only compute: its steps couldn't be recorded, so start a child run for durable work (SPECS.md §13)

The checker doesn't catch this yet; the run fails when it gets there, and so does its test. Outside jobs, in main and in plain functions, tasks can wait, and their waits overlap. See Programs and concurrency.

allDone!(runs) waits for every run in a list and gives their outcomes in the list's order. firstDone!(runs) waits for the first to finish, gives its outcome, and stops the others, which end as Failed(Killed). (all and first are the collection functions; ! never turns them into waits.) A timeout is a run that sleeps, so a question with a deadline of its own is a race between two runs:

eye
job ask(what: String) -> Decision { approval!(what, from: "operator", within: 3 days) }

job timer(d: Duration) -> Decision {
  sleep!(d)
  Expired
}

## Restarts a server if someone approves within the hour.
job restart(server: String) {
  match firstDone!([ask.start!("Restart {server}?"), timer.start!(1 h)]) {
    Completed(Approved(_)) => Log("restarts").add!("{server} restarted")
    Completed(_) | Failed(_) => Log("restarts").add!("{server} left alone")
  }
}
eye
test "firstDone! takes whichever run finishes first" {
  restart.start("db")
  restart.start("web")
  approve("Restart db?")
  advance(1 h)
  expect(Log("restarts").lines == ["db restarted", "web left alone"])
}

When nobody answers about web within the hour, the timer wins and the question is stopped: an answer that comes later finds nothing waiting for it.

lock!(name, for: d, f) keeps work that must not overlap to one run at a time, across every job of the program. A run waits until no other holds the lock, holds it while f runs, and gives it back when f returns:

eye
## Migrates the database. Two migrations must never run at once, so each
## holds the lock "db" while it works.
job migrate(name: String) {
  lock!("db", for: 1 h, fn {
    Log("db").add!("{name} starts")
    sleep!(10 min)
    Log("db").add!("{name} ends")
  })
}
eye
test "a lock lets one migration run at a time" {
  migrate.start("a")
  migrate.start("b")
  advance(30 min)
  expect(Log("db").lines == ["a starts", "a ends", "b starts", "b ends"])
}

The store keeps who holds each lock and until when, so a restart neither frees one nor grants it twice. for: is how long the holder may keep it. If the time runs out while the holder still waits inside f, the holder ends as Failed(LockExpired("db")) and the next run takes the lock, so the work never runs twice at once.

When to write a job ​

Write a job when the work waits, or must finish even if the program restarts: a timeout, a reminder, a call to a service that may be down, a question to a person, a nightly export. Each step is recorded, so the job does each thing once.

Write a plain function for everything else. A function that only computes doesn't need to be durable, and recording its steps would cost for nothing. A job can call it freely, without !. A public function that waits says uses {wait} in its signature, and is called with ! from jobs.

Mistakes this prevents ​

The bugWhy it can't happen
A restart loses a sleeping timer, or a pending stepRuns and their steps are in the journal, and a due run runs on start
A retried step sends a message twiceA recorded step isn't repeated, and an entity call commits with its checkpoint
A wait that hangs foreverLong waits take within:, and their result says time ran out
A hidden pause or side effectEvery durable step is marked with !, and the checker insists
A secret or socket saved to diskOnly values that can be saved live across a !
