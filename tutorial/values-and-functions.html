Values and functions ​

This page covers the everyday core: functions, let, strings, lists, pipes, closures, and the tests that check them. The examples price a shopping basket. Prices are whole cents, an Int, so no rounding gets in the way.

The program is docs/tutorial/code/values-and-functions/main.eye.

Open it in the playground to run it, test it and change it in your browser.

Functions ​

eye
fn double(n: Int) -> Int = n * 2

fn price(cents: Int) -> String {
  let euros = cents / 100
  let rest = cents % 100
  if rest < 10 then "€{euros}.0{rest}" else "€{euros}.{rest}"
}

fn declares a function. Parameters and the result have types: Int, String, and so on.

  • When the body is one expression, write it after =, as in double.
  • When it needs several steps, use braces. The value of the last expression is the result, so price needs no return.
  • if ... then ... else ... is an expression: it has a value, like the ternary operator in other languages.
  • "€{euros}.{rest}" is string interpolation. Any expression can go inside the braces.

Int has arbitrary precision, so it never overflows. / on two Ints rounds down, and % gives the remainder. Long numbers take _ between digits, 1_000_000, and bits read best in hex or binary: 0xFF and 0b1010 are Ints too.

Tests ​

A test block is a declaration, like a function. It has a name and a body, and expect fails the test when its condition is false:

eye
test "functions" {
  expect(double(21) == 42)
  expect(price(250) == "€2.50")
  expect(price(1205) == "€12.05")
}

Run the tests with eye test and the program's directory:

sh
eye test docs/tutorial/code/values-and-functions
text
ok    functions (256µs)
ok    let names a value (1µs)
ok    lists (28µs)
ok    pipes pass the value on (5µs)
ok    closures keep what they capture (2µs)
ok    var and for (2µs)
6 tests passed (295µs)

When an expect fails, it shows the value it got. If double(21) == 42 said 43 instead:

text
FAIL  functions (730µs)
      main.eye:4:3: expected double(21) == 43, but double(21) is 42

1 of 1 test failed

The rest of this page uses tests to show what each line does. Read expect(a == b) as "a is b".

Names with let ​

eye
test "let names a value" {
  let apples = 3
  let each = 40
  let total = apples * each
  expect(total == 120)
  expect("{apples} apples cost {price(total)}" == "3 apples cost €1.20")
}

let gives a value a name. The type is inferred, so you rarely write one inside a body. A let never changes. Trying to change one is an error:

text
main.eye:3:3: total can't change: it is a let or a parameter; declare it with var, or as a mut parameter

A later let with the same name shadows the earlier one, which is often what you want instead.

Lists ​

eye
test "lists" {
  let basket = [250, 120, 80]
  expect(basket[0] == Some(250))
  expect(basket[5] == None)
  expect(basket + [99] == [250, 120, 80, 99])
  expect(basket |> sort == [80, 120, 250])
  expect(basket == [250, 120, 80])
  expect(basket |> size == 3)
}

[250, 120, 80] is a List(Int). Lists are values: adding to one gives you a new list and leaves the old one as it was.

basket[0] doesn't fail when the index is out of range. It returns an Option(Int): Some(250) when the element exists, None when it doesn't. There is no null in Eyelang, and no exception for a bad index. You will see how to take an Option apart on the next page.

Pipes ​

x |> f(y) calls f(x, y): the value on the left becomes the first argument. Long chains read top to bottom, in the order things happen:

eye
fn total(basket: List(Int)) -> Int = basket |> sum

fn bargains(basket: List(Int), under: Int) -> List(String) = basket
  |> filter(fn cents: cents < under)
  |> sort
  |> map(price)

filter keeps the prices under the limit, sort puts them in order, and map turns each one into a string with price. A line that starts with |> continues the line before it.

eye
test "pipes pass the value on" {
  let basket = [250, 120, 80]
  expect(total(basket) == 450)
  expect(bargains(basket, under: 200) == ["€0.80", "€1.20"])
  expect(basket |> map(double) == [500, 240, 160])
}

The collection functions, size, sum, filter, map, sort and the rest, take the collection first so they work well after |>. They are listed in built-in functions.

Arguments can be passed by name, as in bargains(basket, under: 200). That helps when the meaning of a number isn't obvious at the call.

Closures ​

fn cents: ... is a function without a name, a lambda. You already passed one to filter. A lambda can use names from where it was written, and keeps their values:

eye
fn discount(percent: Int) = fn cents: cents - cents * percent / 100

test "closures keep what they capture" {
  let tenOff = discount(10)
  expect(tenOff(250) == 225)
  expect([250, 120] |> map(tenOff) == [225, 108])
}

discount(10) returns a function that takes ten percent off. discount has no -> type; for a private function, Eyelang infers the result and even the parameter types. Public functions (pub fn) write out their full signature.

var and for ​

Most code doesn't need a variable that changes. When it does, use var:

eye
fn countOver(basket: List(Int), limit: Int) -> Int {
  var count = 0
  for cents in basket {
    if cents > limit then count += 1
  }
  count
}

test "var and for" {
  expect(countOver([250, 120, 80], limit: 100) == 2)
  var sum = 0
  for i in 1..=4 { sum += i }
  expect(sum == 10)
  var basket = [250, 120, 80]
  basket[1] = 99
  basket[2] += 1
  expect(basket == [250, 99, 81])
}
  • var declares a variable that can change. += adds to it.
  • for x in xs { ... } runs the block once for each element. 1..=4 is a range that includes 4; 1..4 stops before it.
  • if ... then ... with a single statement needs no braces.
  • basket[1] = 99 changes one element of a var list, and basket[2] += 1 adds to one. The element must be there: an index past the end stops the program, as a bug, since a change that went nowhere would be lost. Add elements with +=, as in basket += [99].

A var is local, and nothing else can see it change. A lambda given straight to a call, such as xs |> filter(fn x: x < total), may read it, and sees its value at the call; a lambda kept in a let or returned can't capture it. Mutation explains why that rules out a whole class of bugs.
