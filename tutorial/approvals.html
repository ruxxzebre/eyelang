All together: approvals ​

This page walks through one larger program: temporary access, granted by a person. Someone asks to join a group, say prod-db, for two hours. A model writes a one-line summary for the approver. The approver gets a message with Allow and Deny buttons. If they allow it, the program adds the person to the group, and two hours later takes them out again. Every weekday morning the approver hears how many requests are still waiting.

Programs like this are usually built from several parts: a database table for the requests, a queue and a worker for the slow steps, a cron job that looks for expired access, retry loops around every HTTP call, and a test setup that mocks the clock. In Eyelang it is one program of about 300 lines with comments, plus 100 lines of tests, and the language checks the parts that usually go wrong: that state changes are atomic, that a retry can't do something twice, that every failure is handled, and that a wait of three days survives a restart.

The program is in docs/tutorial/code/approvals. Its tests check everything this page says. Run them from the repository's root:

sh
eye test docs/tutorial/code/approvals

ok    the approver allows, and the access ends when its time is up (2.182ms)
ok    the approver says no (1.226ms)

ok    a lost reply from the access service is settled by asking, not by granting again (427µs)

The tests cover three days of waiting, a two-hour grant and a weekend, and they take a few milliseconds.

The services it talks to ​

A contract describes another service: its operations, their types, and how they go over HTTP. Here is the chat service:

eye
@auth(bearer: "notify-token")
contract Notify {
  ## Sends a message to one person. Notify keeps what each key did, so sending
  ## again with the same key is how a lost reply is settled.
  @http("POST /v1/send", status: { 200: Accepted, 400: Refused })
  @key(required)
  @reconcile(send)
  command send(to: UserId, text: String) -> Delivery

  ## Asks one person, with 2 to 4 buttons. The question closes after
  ## `within`; an answer comes as an `answered` event.
  @http("POST /v1/ask")
  @key(required)
  @reconcile(ask)
  command ask(to: UserId, text: String, choices: List(Choice), within: Duration) -> Asked

  @key(question)
  event answered: Answered on "notify.answers"
}

Four things in it matter for the rest of the program:

  • @auth(bearer: "notify-token") means every request to Notify carries a secret, and Notify sends the same secret with the answered events it sends the program, so nobody else can answer for the approver.
  • @key(required) means every call carries a key. The service remembers what it did with each key, so asking again with the same key can't send a second message.
  • @reconcile(send) says how to find out what happened when a reply is lost: send again with the same key, and the service answers without acting twice.
  • Every command can also return Uncertain(key): the request went out, but the reply didn't come back. The compiler won't let you use the result until you have dealt with that case, either by calling .reconcile!() or by matching Uncertain(_) yourself.

The access service works the same way, but finds lost grants with a query instead of sending again:

eye
contract Access {
  ## Adds a person to a group. The service remembers what each key did.
  @http("POST /v1/grants")
  @key(required)
  @reconcile(grantFor)
  command grant(person: UserId, group: String) -> Membership

  ## What the grant with this key did, or None if it never arrived.
  @http("GET /v1/grants/by-key/:key")
  query grantFor(key: Key) -> Option(Membership)

  ## Takes a person out of a group again.
  @http("POST /v1/grants/:grant/revoke")
  @key(required)
  @reconcile(revoke)
  command revoke(grant: GrantId) -> Removal
}

A typical HTTP client returns a status code or throws, and you decide in each place whether a timeout means "retry" or "give up". Here the contract decides once, and a command is never sent twice on a guess. A request that never reached the service is simply sent again. A request whose reply was lost is resolved by asking its owner.

A request has one owner ​

The request's state lives in an entity: one Request per id, with its own fields and methods.

eye
pub type RequestId = | RequestId(String)

## What someone asks for.
pub type Details = {
  person: UserId,
  ## A group in the access service, such as "prod-db".
  group: String,
  reason: String,
  lasting: Duration,
}
eye
pub type Status =
  | New
  | Waiting
  | Denied(why: String)
  | Unanswered
  | Active(grant: Grant, until: Instant)
  | Ended

entity Request(id: RequestId) {
  state details: Option(Details) = None
  state status: Status = New
  state summary: String = ""
  state reminders: Int = 0

  ## Takes a request in and starts its review, in one transaction. Sending
  ## the same request again changes nothing and starts nothing.
  pub fn submit(d: Details) uses {start review} {
    if status != New { return }
    details = Some(d)
    match admissible(d) {
      Ok(_) => {
        status = Waiting
        review.start(id, d, key: "review-{id}")
      }
      Err(why) => status = Denied(why: "{why}")
    }
  }

  pub fn summarise(text: String) { summary = text }

  pub fn remind() { reminders += 1 }

  pub fn activate(g: Grant, until: Instant) { status = Active(grant: g, until:) }

  pub fn close(s: Status) { status = s }
}

Each method is a transaction. One caller at a time changes a given request, and a method either commits completely or not at all. submit does two things in one transaction: it records the request, and it starts the review job. If the transaction rolls back, the job never starts. If the job starts, the request is recorded.

With a database and a queue, those are two writes to two systems, so a crash between them leaves a recorded request that nobody reviews, or a review for a request that isn't recorded. The usual fix is an outbox table and a relay process. Here the language handles it.

submit is also safe to call twice. A request that isn't New any more ignores it, so a double-clicked button or a retried webhook starts one review.

Rules are pure functions ​

Which groups can be asked for, and for how long, is plain code:

eye
## The groups that can be asked for, and the longest each can be held.
let groups: Map(String, Duration) = { "prod-db": 4 h, "billing": 8 h, "vpn-admin": 1 h }

pub type Inadmissible =
  | UnknownGroup(String)
  | TooLong(most: Duration)

## Checks a request against the rules before anyone is asked.
pub fn admissible(d: Details) -> Result((), Inadmissible) {
  let Some(most) = groups[d.group] else { return Err(UnknownGroup(d.group)) }
  if d.lasting > most { return Err(TooLong(most:)) }
  Ok(())
}

admissible is public and has no uses clause, so the compiler holds it to being pure: it can't read the clock, a file or the network. If someone later adds a rule like "no prod access after six in the evening", the signature has to change, and the change shows in review:

text
main.eye:40:1: admissible uses clock, which its signature doesn't list: run eye fmt, or add uses {clock}

The review: a job that waits ​

The review is a job: a function that can pause for as long as it needs, and that keeps no memory or thread while it waits.

eye
let allow: Choice = { id: "allow", label: "Allow" }
let deny: Choice = { id: "deny", label: "Deny" }

type ReviewError =
  | NotAsked(reason: String)
  | NotGranted(group: String)

## Reviews one request: a summary from the model, a question to the approver,
## then the grant. The approver gets one question at a time, in the order the
## requests came in.
@concurrency(1)
@unwitnessed("Notify declines to ask only when the approver has no device, which no recording has")
job review(id: RequestId, d: Details) -> Result(Status, ReviewError) {
  let summary = summarise!(d)
  Request(id).summarise!(summary.text)
  let asked = notify.ask!(
    to: approver,
    text: "{d.person} asks for {d.group} for {d.lasting} ({describe(summary.risk)}). {summary.text}",
    choices: [allow, deny],
    within: 3 days,
    key: "review-{id}",
  ).reconcile!()
  let question = match asked {
    Asking(q) => q
    NotAsked(reason) => return Err(NotAsked(reason))
  }
  let Some(answer) = next!(notify.answered, where: fn a: a.question == question, within: 3 days) else {
    Request(id).close!(Unanswered)
    tell!(d.person, "Nobody answered your request for {d.group}. Ask again if you still need it.", key: "unanswered-{id}")
    return Ok(Unanswered)
  }
  if answer.choice == deny.id {
    let denied = Denied(why: "{answer.by} said no")
    Request(id).close!(denied)
    tell!(d.person, "Your request for {d.group} was denied.", key: "denied-{id}")
    return Ok(denied)
  }
  let until = now!() + d.lasting
  match access.grant!(d.person, d.group, key: "grant-{id}").reconcile!() {
    Added(grant) => {
      Request(id).activate!(grant, until)
      tell!(d.person, "You are in {d.group} until {until.time(in: dublin)}.", key: "granted-{id}")
      Ok(Active(grant:, until:))
    }
    NoSuchGroup => Err(NotGranted(d.group))
  }
}

Read it top to bottom, the way it runs:

  1. summarise!(d) asks a model for a summary (shown below).
  2. notify.ask!(…) sends the question with two buttons. The key review-{id} makes it safe to repeat. .reconcile!() resolves a lost reply before the program goes on.
  3. next!(notify.answered, …, within: 3 days) waits up to three days for the approver to press a button. It returns None if nobody does.
  4. access.grant!(…).reconcile!() adds the person to the group, with its own key.

Every ! is a checkpoint. Its result is saved before the job goes on. If the program restarts while the job waits on next!, the job resumes at that line with the same question in hand. The model isn't called again and the question isn't sent again. The pauses are all visible: a reviewer can see every point where this job can stop or touch the outside world by looking for !. Leave one out and the checker says so:

text
main.eye:149:17: summarise waits, so calling it is a durable step: write summarise!(…)
main.eye:206:3: in a job, an entity call is a durable step: write close!(…)

@concurrency(1) makes the approver get one question at a time, in the order the requests came in. A second request's run queues until the first one finishes, and keeps its place in line while it waits.

The alternative is usually a pending_reviews table with a state column, a worker that polls it, an asked_at timestamp, a cron job that expires old rows, and code to make sure two workers don't take the same row. The job above is that state machine, written as straight-line code.

Failures are values ​

Nothing in Eyelang throws. Every failure is a value in a type, and every match must cover all of its cases. The program uses this in three places.

The model. ai.generate! names the type it wants, and the compiler derives a JSON Schema from it. The reply is checked against the schema and decoded into a Summary, or it is an Err:

eye
## What the approver reads about a request, written by a model.
type Summary = {
  ## One sentence, at most 20 words: who wants what, and why.
  text: String,
  risk: Risk,
}

type Risk =
  | Low
  | Medium
  ## Production data, money or admin rights.
  | High(reason: String)

let instructions = """
  You help an operator review requests for temporary access to a group.
  Summarise the request in one sentence and rate its risk. Production data,
  money and admin rights are never Low. Use only what the request says.
  """

## Asks a model to summarise a request. If the model fails, the approver
## gets the request without a summary rather than no request at all.
fn summarise(d: Details) -> Summary {
  let reply: Result(Summary, ai.AiError) = ai.generate!(
    model: "claude-sonnet-5-5",
    system: instructions,
    prompt: d |> toJson,
  )
  match reply {
    Ok(summary) => summary
    Err(e) => { text: "No summary: the model failed ({e}).", risk: Medium }
  }
}

fn describe(r: Risk) -> String = match r {
  Low => "low risk"
  Medium => "medium risk"
  High(reason) => "HIGH RISK: {reason}"
}

If the model is down or answers with something that doesn't fit, the approver still gets the request, without a summary. That is a decision written in the code, not a stack trace in a log. The ## comments on Summary and Risk become descriptions in the schema the model sees.

The services. The match on access.grant! handles Added and NoSuchGroup. Remove .reconcile!() and the checker points out the case you would be missing:

text
main.eye:174:3: this match doesn't handle Uncertain(_): add an arm for it, or `_ => …`

Your own types. Add a fourth risk level, Critical, and every match on Risk, such as describe, stops compiling until it says what to do with it:

text
main.eye:130:34: this match doesn't handle Critical: add an arm for it, or `_ => …`

Effects show in signatures ​

tell sends a person a message. It is public, so its signature lists everything it can do:

eye
## Tells a person how their request went. Notify keeps what each key did, so
## a lost reply is settled by sending again with the same key.
@unwitnessed("Notify refuses a send only for a person it doesn't know, which no recording has")
pub fn tell(person: UserId, text: String, key: Key) uses {wait, net Notify.send} {
  match notify.send!(to: person, text:, key:).reconcile!() {
    Accepted(_) => ()
    Refused(error) => log.warn("Notify refused {key}: {error}")
  }
}

uses {wait, net Notify.send} says it is a durable step and that it calls exactly one operation of one service. If it also asked a question, net Notify.ask would have to appear here too. A new permission can't sneak in without changing a signature that a reviewer sees.

Taking access away: a view and a sleeping job ​

A view is a named query over entities that the runtime keeps up to date as transactions commit:

eye
## Every request whose access has been granted and not yet taken away.
view active = Request.all
  |> filter(fn r: match r.status {
    Active(..) => true
    _ => false
  })

@on(enters(active)) starts one run of expire for each request that becomes active:

eye
## Every request that becomes active gets one run of this job. It sleeps
## until the access runs out, then takes it away.
@on(enters(active))
job expire(r: Ref(Request)) {
  let Active(grant, until) = r.read!().status else { return }
  sleepUntil!(until)
  match access.revoke!(grant.id, key: "revoke-{grant.id}").reconcile!() {
    Removed | AlreadyGone => ()
  }
  r.close!(Ended)
  tell!(grant.person, "Your access to {grant.group} has ended.", key: "ended-{grant.id}")
}

sleepUntil!(until) waits two hours, or eight, or a week. While it waits, the run is a few hundred bytes in the journal, not a thread or a timer in memory. This replaces the usual cron job that runs every minute, scans a table for rows where expires_at < now(), and must be written so that two overlapping runs don't revoke twice. Here the revoke has a key, and each grant gets exactly one run.

Weekday mornings: a schedule ​

eye
## On weekday mornings the approver hears how many requests are waiting.
@on(weekdays(09:00, in: dublin))
job morning(day: Date) {
  let open = Request.all.read!() |> filter(fn r: r.status == Waiting)
  if open == [] { return }
  for r in open { Request(r.id).remind!() }
  tell!(approver, "{open |> size} access requests are waiting for you.", key: "waiting-{day}")
}

weekdays(09:00, in: dublin) fires at nine on Irish time, Monday to Friday, through daylight saving changes. The job gets the date of the firing, which goes into the message's key, so whatever happens to that run, the approver gets one message a day.

main ​

main is an ordinary function that runs each time the program starts. It submits one request from the command line:

eye
## Submits one request from the command line, for example
## `eye run . -- r-1 ann prod-db 2 "fix the stuck migration"`. Running it
## again with the same id changes nothing.
pub fn main(args: List(String)) -> Result((), String) uses {entity Request, start review} {
  let usage = "usage: eye run . -- ID PERSON GROUP HOURS REASON"
  let (Some(id), Some(person), Some(group), Some(hours), Some(reason)) = (args[1], args[2], args[3], args[4], args[5]) else {
    return Err(usage)
  }
  let n = parseInt(hours).mapErr(fn _: usage)?
  Request(RequestId(id)).submit({ person: UserId(person), group, reason, lasting: 1 h * n })
  Ok(())
}

It calls an entity method that starts the review, so its signature says uses {entity Request, start review}. Because submit ignores a request it has seen, and starts the review with a key, running the program again with the same arguments changes nothing.

Tests that play out days in milliseconds ​

Tests run against an in-memory store with a clock that moves only when the test says so. Calls to other services replay recordings of real answers. Here is the whole happy path, from request to expiry:

eye
let ann = UserId("ann")
let first = RequestId("r-1")

let fix: Details = {
  person: ann,
  group: "prod-db",
  reason: "Fix the stuck migration",
  lasting: 2 h,
}

fn answer(q: String, choice: String) {
  notify.answered.publish({ question: notify.QuestionId(q), choice, by: approver, at: now() })
}
eye
test "the approver allows, and the access ends when its time is up" {
  with fakes(ai, notify, access, from: "recordings/")
  with clock(2026-10-12 10:00 in dublin)
  let r = Request(first)
  r.submit(fix)
  expect(r.status == Waiting)
  expect(r.summary == "Ann wants two hours on the production database to fix a stuck migration.")
  answer("q-1", "allow")
  expect(r.status == Active(grant: { id: access.GrantId("g-1"), person: ann, group: "prod-db" }, until: 2026-10-12 12:00 in dublin))
  advance(119 min)
  expect(r.status != Ended)
  advance(1 min)
  expect(r.status == Ended)
}
  • with clock(…) starts the test's clock at a fixed time, and advance(119 min) moves it. Every run that wakes on the way runs before advance returns, so the test can check the state right after.
  • notify.answered.publish(…) stands in for the approver pressing a button. The waiting review wakes at once.
  • with fakes(ai, notify, access, from: "recordings/") answers each call from a recording, matched by operation and key, and checked against the contract when it is loaded.

The recordings are also what eye check trusts about the services. Reading a field that no recording has is an error, since nothing shows the service ever sends it. No recording here has Notify declining to ask, so review reads NotAsked(reason) only because it is marked @unwitnessed("…"), with the reason the author believes it can happen. Matching a variant without reading its fields, as NoSuchGroup or Refused(_), needs no mark.

The recording for the access service includes a grant whose reply was lost:

json
{
  "contract": "Access",
  "exchanges": [
    {
      "op": "grant",
      "key": "grant-r-1",

The test for it checks that the program asks grantFor with the same key, finds the grant that did land, and goes on, without granting a second time:

eye
test "a lost reply from the access service is settled by asking, not by granting again" {
  with fakes(ai, notify, access, from: "recordings/")
  let r = Request(RequestId("r-2"))
  r.submit({ person: UserId("bob"), group: "billing", reason: "Check an invoice", lasting: 1 h })
  answer("q-2", "allow")
  let Active(grant, ..) = r.status else { unreachable("the request should be active") }
  expect(grant.id == access.GrantId("g-2"))
}

Waiting three days, and a weekend, cost nothing either:

eye
test "a request nobody answers for three days is closed" {
  with fakes(ai, notify, from: "recordings/")
  with clock(2026-10-16 10:00 in dublin)  # a Friday
  Request(first).submit(fix)
  advance(71 h)
  expect(Request(first).status == Waiting)
  advance(1 h)
  expect(Request(first).status == Unanswered)
}
eye
test "on weekday mornings the approver hears what is waiting" {
  with fakes(ai, notify, from: "recordings/")
  with clock(2026-10-16 08:00 in dublin)  # a Friday
  Request(first).submit(fix)
  advance(1 h)
  expect(Request(first).reminders == 1)
  advance(2 days)  # Saturday and Sunday bring no reminder
  expect(Request(first).reminders == 1)
}

There is no sleep in these tests, no retry, and no mock of Date.now. They give the same result on every run, on any machine, in any time zone.

Run it for real ​

eye run runs main, then keeps the program's jobs going and saves everything to a journal in .eye/journal. It reads each service's address from the environment: NOTIFY_URL, ACCESS_URL, and AI_URL for an OpenAI-compatible model gateway; Notify's secret from NOTIFY_TOKEN; and the port Notify sends its answers to from EYE_EVENTS_PORT (more on that below). The run below used small local stand-ins for the three services.

sh
cd docs/tutorial/code/approvals
NOTIFY_TOKEN=… EYE_EVENTS_PORT=8080 eye run . -- r-1 ann prod-db 2 "fix the stuck migration"

The answer comes in as an event ​

When the approver presses a button, Notify sends the program its answered event, as an HTTP POST to /events/notify.answers with the event as JSON and Notify's secret. The program takes events on the port EYE_EVENTS_PORT names, and says so when it starts:

text
eye run: taking notify.answered on :8080

Without EYE_EVENTS_PORT, it says that notify.answered has no way in, and the review would wait out its three days. Here curl plays Notify's part:

text
$ curl -i -X POST http://127.0.0.1:8080/events/notify.answers \
    -H "Authorization: Bearer $NOTIFY_TOKEN" \
    -d '{"question": "q-1", "choice": "allow", "by": "paul", "at": "2026-10-12T09:15:00Z"}'
HTTP/1.1 202 Accepted

The 202 comes once the event is in the journal. The waiting review wakes, grants the access and tells Ann, and the access job sleeps until the two hours are up:

text
$ eye runs .
#1 review("r-1", { person: "ann", group: "prod-db", reason: "fix the stuck migration", lasting: 2 h })  done: Ok(Active(grant: { id: "g-1", person: "ann", group: "prod-db" }, until: …  [11 steps, 3.5 KiB, 120 tokens in, 30 out, $0.0005]
#2 expire(Request("r-1"))  sleeping until 2026-10-13 02:14:37 (in 1h59m58s)  [2 steps, 1.2 KiB]

A request without the secret gets 401 and reaches no code, so nobody but Notify can answer for the approver. Notify may send an event again if its reply was lost; the event's @key(question) makes the second one start nothing. A Notify written in Eyelang sends its events itself (see Running in production), and one written in Go or TypeScript calls the sender eye gen writes for it.

eye approve answers only approval!, which this program doesn't use.
