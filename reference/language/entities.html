Entities ​

eye
@version(3)
entity Player(id: PlayerId) {
  state name: String = ""                    # v3: renamed from nick
  state devices: Set(DeviceId) = {}          # v3: added

  pub fn addDevice(d: DeviceId) -> Result((), DeviceError) {
    if devices |> size >= 5 { return Err(TooManyDevices) }
    devices = devices |> add(d)
    Ok(())
  }

  pub fn retire(ok: Approval) { end(ok) }     # ending an entity needs an Approval

  migrate from 2 (old) {                      # pure function from the old stored shape
    { name: old.nick, devices: {} }
  }
}

  • Identity: Player(id) is a reference. The entity exists on first use, starting from default state.

  • State is saved, so its types have Save. A state field can't hold a function, a Secret or anything else without Save: the store keeps every entity's state, and a function is code that the next version of the program may not have. A Ref is saved as its identity.

  • Methods are atomic transactions. One writer at a time per entity, all or nothing. A method may call methods on other entities, and the whole call tree commits or rolls back together. An Err is a value like any other: a method that returns one commits what it changed. Only a fault (section 15), such as unreachable, rolls the call tree back, and with it the jobs it started and the events it published, which never happen.

  • A call tree that comes back to an entity shares its state. The call tree is one transaction, and in it each entity has one state in progress, which every call on the entity reads and changes. A call that comes back to an entity whose method is still running is not a second writer: it starts from what the tree has changed so far, and the entity commits once, with every change.

    eye
    entity Ping(id: String) {
  state n: Int = 0

  pub fn ping() -> Int uses {entity Ping, entity Pong} {
    n += 1
    let before = n   # 1
    Pong(id).pong()  # comes back to bump, which sees n == 1 and makes it 2
    n                # 2; before is still 1
  }

  pub fn bump() { n += 1 }
}

entity Pong(id: String) {
  pub fn pong() uses {entity Ping} { Ping(id).bump() }
}

    After Ping("x").ping(), Ping("x").n is 2, at version 1.

    • The outer method goes on from the inner call's changes. A method's state is its mut self (section 7), and a call that may come back to the entity passes it on, the way unpin(p) passes it to another method of the entity: the call takes the state as it is and gives it back changed. So after Pong(id).pong() returns, n in ping reads 2. A value read before the call keeps what it read, as values do: before stays 1. So does the first n in n = n + c.more(), when the call c.more() comes back and changes n: the assignment writes over that change. n += x evaluates x before it reads n, so n += c.more() keeps both.
    • Reads in the tree see the state in progress. Ping(id).n or Ping(id).read() in pong gives ping's changes so far, at the version the entity was loaded at; nothing outside the tree sees them until it commits.
    • An end in a call that comes back ends the entity for the whole tree. When pong calls a method of Ping that runs end(ok), Ping ends when the tree commits. Its methods still running, such as ping, run to the end, and what they change after the end is dropped with the rest of the state, as in the method that called end; a new call on Ping, or a read of it, in the same tree faults.
    • Jobs and events from every level commit together. A job started or an event published in any call of the tree, on any entity, starts or is published when the tree commits, in the order the calls made them; a fault anywhere in the tree drops all of them with every entity's changes.

  • Ending an entity needs an Approval. end(ok) in one of the entity's methods ends it when the transaction commits. ok is an Approval, which only approval! makes (section 15), so retiring an entity takes a person's consent, and end without one doesn't compile. The Approval isn't matched against the entity: it shows that a person said yes, and the store keeps its what and by, with when the entity ended, for the record.

    • end is resolved by context. In an entity's own method, end(…) is the entity's, as its methods are, unless a local, a state field or a method of that name is nearer. Elsewhere end is a string's end position, s.end(). end can't be called on another entity, which ends itself through a method of its own, such as retire; the checker says so.
    • What an ended entity is. Its state is gone, and the store keeps only that it ended, when, and the approval's what and by. It leaves every view, so @on(leaves(…)) jobs start, and Player.all no longer lists it. Its Ref stays a valid value whose identity can be read (p.id), but calling a method on it or reading it (read(), a state field) faults: Player("ann") ended at 2026-10-12 09:00 UTC, approved by operator ("Retire ann?"), so it can't be read or changed. The identity stays ended: using it never starts the entity again, so a job holding an old reference can't bring it back by mistake. A leaves job that the end starts gets the reference; what it needs of the state is passed on before the end.
    • What the method changes after end(ok) is dropped with the rest of the state, and a later call on the entity in the same transaction faults.

  • State and mut self: an entity method is a mut self method over the entity's state (section 7). A state field such as devices is short for self.devices, and a method is called by its name too: unpin(p) in another method is self.unpin(p), in the same transaction. A pipe still calls a function, never a method: shapes |> add(s) is the collection function add, even in an entity that has a method of that name. The state is loaded when the transaction first calls the entity and saved when it commits; nothing outside the transaction sees a change until the commit.

    • A method's callbacks may read state fields, as they may read a var (section 7): players |> filter(fn p: p != owner). A callback gets each field's value as it was at the call, and can't change one: a closure can't change the entity's state. A closure kept in a let or returned can't capture the state, since it could run after the state changed: a closure can't capture owner, the state of the entity, unless it is a callback given straight to a call.

  • Methods stay inside the program. A method is a transaction, and the runtime may run one again after a conflict, so it does only what can happen twice without anyone outside seeing it: it changes its state, calls pure code and other entities' methods, ends its entity with end(ok), starts jobs (wake.start(id)) and publishes events. A job begins, and an event is sent, only if the transaction commits. A method never waits and never reaches outside the program: a call that uses net, fs, process, clock, random, env, ffi, secret or wait, itself or through the functions it calls, is an error that names the effect and says where the call belongs: now uses clock, which an entity method can't: it runs as a transaction, which may run again after a conflict, so what reaches outside the program or waits belongs in a job, which the method can start. A method that needs the time takes it as an argument, which a job reads with now!(), so a retry sees the same time.

    • Output is allowed. print and log.info write their line again when a transaction is retried, which is harmless: output is for people watching, not part of what the method computes (section 12).
    • A served operation (impl Contract, section 17) is a transaction too, and follows the same rule.

  • Reading from a job: w.read!() returns a snapshot, whose type is the entity's name (fn due(me: Traveller) takes one): the entity's state, its identity and a version field, a Version that counts the transactions that changed the entity: 0 when it is new, then one more for each. Snapshots go stale, and commands can name the version they were based on (see @fresh in section 17). Outside a job, in a test for instance, w.read() gives a snapshot without !; in a transaction that has called w, it gives the state in progress. Since the snapshot's version is the transactions', a state field can't be named version: a snapshot's version counts the transactions that changed Doc, so a state field can't be named version: name it revision, or what it counts.

    • A field of a reference. Outside jobs, w.phase is short for w.read().phase. In a job, and in a waiting function, it would read the entity without recording it, so a resumed run could see another value; it is an error that says to read a snapshot: in a job, w.phase reads World without recording it, so a resumed run could see another value: read a snapshot with w.read!() and take phase from it. The identity, w.id, reads without loading the entity, so it is allowed everywhere. A job reads views and World.all with read!() too (section 15).

  • Evolution: @version(N) numbers the shape of an entity's stored state (1 without it), and every row records the version it was saved with; it isn't the snapshot's version, which counts transactions.

    • Adding a field with a default needs no new version: a row without the field gets the default when it is loaded, and a field the entity no longer declares is dropped.
    • Any other change, such as a rename or a new field without a default, raises @version by one and adds migrate from the old version: a pure function from the row as it was stored at that version to the state at the next one. old is that row; the old shape isn't declared anywhere, so its fields are read by name and checked when the migration runs. The migration to the current version gives the state the entity declares, which the checker holds it to: every field without a default, each of its type. An older one gives the next version's shape.
    • Migrations chain. A row saved at version 1 of a version-3 entity runs migrate from 1, then migrate from 2, when it is next loaded, and is saved at version 3 the next time a transaction changes it. So an entity has a migration from each version between its oldest one and the current one, with no gaps; dropping the oldest migrations retires the rows saved before them.
    • eye run reads every stored row's version before it starts, and refuses to start if one is newer than the program's or older than its oldest migration: 3 Player saved at version 1, and Player has no migrate from 1.
