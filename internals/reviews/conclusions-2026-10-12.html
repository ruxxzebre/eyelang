Conclusions from the reviews of 2026-10-12 ​

What the coordinating session concluded from the spec review and the performance and package-manager analysis, and what it proposes to do about each finding. Sections 1 to 5 are about the spec review; section 6 is about performance and packages.

The short version ​

The spec is in good shape as a design and in poor shape as a reference. Its ideas hold: none of the findings argues against a pillar. But the code has moved faster than the text. Four findings are correctness bugs that let an ordinary program do the wrong thing without a word, and they come first. After them come a handful of language decisions that only the owner can make, then one sweep of the text.

1. Correctness bugs: fix first ​

These break a pillar in programs that look right. Each becomes a task with an issue; none needs a new idea, only the rule SPECS already implies, enforced.

2. Decisions for the owner ​

Each of these changes what ordinary programs look like, so it goes to the owner first. The recommendation is given; nothing is built until the owner agrees.

Decided by the owner on 2026-10-12: 1 (results and outcomes can't be dropped silently: task G.12, #95) and 5 (the waits are named allDone! and firstDone!, built by C.2). The owner also confirmed C.8's choices: text that matches no waiting approval is refused, an answer with no by comes from the person asked, and who may publish an event is open question 35. Later the same day the owner decided the rest: 2 as recommended (G.13, #96), 3 as recommended (G.14, #97), 4 as option (b), any function callable as a method on its first argument, since pipes are rare in practice (G.15, #98), and 6 as recommended (G.16, #99).

  1. Results and outcomes can't be dropped silently (finding 7). Recommend yes: a statement whose value is a Result or a command's outcome must be used, matched or discarded with let _ = …. It is the easy-but-wrong program "How to decide" item 1 is about, and the tour itself has it. Cost: a let _ = where a program means to ignore a failure.
  2. Reading a var in a callback (design risk 4). Recommend yes, for callbacks only (a function given to a parameter, which can't outlive the call): it reads the variable's value at the call. Stored functions keep the rule. Under value semantics this can't alias, and the loop it unblocks is one of the commonest shapes there is.
  3. Record literals in lambdas and pipelines (design risk 3, open question 25). Recommend letting a lambda's body take its record type from where the result goes, which is the rule literals already follow, rather than new syntax at the literal. If that isn't enough, then User { … }.
  4. Built-in collection functions as methods (finding 10). xs.first() and xs |> first both work today, against "one obvious way". Recommend keeping only the pipe form and letting eye fix rewrite the method form, or else writing the method form into SPECS as the rule for every function whose first parameter is the receiver. Either is defensible; two spellings for built-ins only is not.
  5. Overloaded names (design risk 11). Recommend renaming the waits that clash with collection functions (all! and first! resolve to all and first today) before C.2 builds them, and adding a glossary to SPECS. C.2 is being built now, so this needs an answer soon; until then the worker builds them under their spec names.
  6. Division by NonZero (design risk 5). Recommend keeping the rule and adding the helpers that make the common cases short (average, and div returning an Option), rather than relaxing it.
  7. Events have no caller guard (gap, and design risk 7). Recommend an open question first: who may publish an event, and whether approval answers need a typed identity from the contract that delivers the press rather than text. C.8's worker was asked to write this into SPECS as an open question rather than build a mechanism.

3. The text: one sweep ​

A single task (G.11) that changes no behaviour:

  • the stale rows and paragraphs of finding 8 (SQL, resume from the start, checkpoints at every !, the Store interface, Q24's premise, @priority, row 117's reference, §21);
  • a short rule for waiting functions (finding 5), which open question 23 then builds on;
  • the rules the code chose and SPECS never recorded (finding 10): unprefixed imported variants, state fields captured in entity lambdas, a state version field (make it an error), faults beyond the six listed, which standard modules need import, how ranges end and wrap;
  • the contradictions in the full list (function types without uses, the newline and brace lists, impls of a contract from another module, ports against NOTIFY_URL);
  • the open questions: mark each decided one "Decided: see the decision log" in place, keeping its number, and keep only the residual part open (numbers never change again);
  • a glossary (checkpoint, run, step, key, version, handler);
  • the decision log split into language and runtime/tooling, with lab histories moved to the design pages, and implementation detail (buckets, advisory locks, environment variables) moved to docs/internals.

The broken examples of finding 9 are fixed by C.7, which makes every SPECS example check in a context; that task is next in the queue.

4. What is already done ​

Found by the review and fixed the same day, or fixed by work that was already under way: Type.f() through another module (G.4), a type alias that names itself (G.5), impl on an entity (G.6), cron and the schedule policies (C.3), @fresh and @destructive, which also gave Version a type (6.3), and serving a contract over HTTP (6.13).

5. Where the spec review stands ​

G.7 to G.17 are filed under "Core gaps" in ROADMAP. Done: G.9 (re-entrant calls), G.11 (the sweep), G.16 (average and div), and the review's examples move to C.7. Being built: G.7, G.8 and G.10 (the effect rules) and C.7. Waiting for the effect rules to land, since they change the same checker code: G.12 to G.15 and G.17.

6. Performance and packages ​

What the numbers say ​

The interpreter's constant speed (2–9× slower than CPython) is fine for programs that mostly wait. The six slowdowns that grow with the input are not: they turn ordinary programs (a string built with +=, a word count in a map, a binary tree, ten thousand waiting runs) from milliseconds into seconds or minutes, and three of them sit in exactly the part of the system the language is for. They come before more compiler work, because v0.4 keeps the Go runner and the store, where most of them live. Three were prototyped in about 30 lines with large measured wins.

So a new group of tasks, R.1 to R.7 ("Runtime at scale"), goes ahead of 7.5:

TaskWhatMeasured or expected
R.1Exhaustiveness uses the default matrix when no row tests a column (check/exhaust.go)9.4 s to 13 ms on a tree match (prototyped)
R.2Waking runs: a timer min-heap and an index by event in the waiting index, and the store touches its event list only when a commit changes it10k waiting runs: 25.8 s to 4.2 s (prototyped), under 1 s expected with the heap
R.3A persistent hash map (HAMT) behind Map and Set, so replacing a key's value and every entity write are O(log n)the map-counter idiom and entity writes stop being quadratic
R.4String append shares spare room the way list append does+= on strings becomes amortised O(1)
R.5The journal stores run records as raw JSON, keeps the 20-step trail out of every commit, and groups commits in burstscommits 3–5× smaller; 5k starts from main in about 1 s instead of 4.5 s
R.6The call path: bindings precomputed, closures and fieldless variants cached, return and break without panics, fast equal, shared record names2–3× on call- and record-heavy code
R.7A waiting run's record leaves RAM: only (id, wakeAt, event) stays, the record loads on wakethe pillar "waiting costs no memory" becomes true, not "about 1.5 KB"

Also, at once and without a task: SPECS §1's "a waiting job holds no memory at all" is reworded to what is true (no thread, and its saved record, about 1.5 KB, until R.7), and docs/internals/compilation.md's stale "What exists today" lines (quadratic xs += [x], typeOf) are corrected.

The idea ​

The analysis agrees with the direction: compile-time-checked determinism for durable code, single-writer entities with value semantics, exactly-once made explicit in types, contracts that derive network policy, and deterministic tests are a real step past Temporal, Restate and Durable Objects. Its warning is about scope: one team is carrying a durable engine, an actor runtime, a migration system and cron at once. The answer is the one the roadmap already takes: the lab's workloads decide what gets built, and each piece stays small.

Decisions for the owner ​

  1. How the Go runner hosts compiled code (7.6). The analysis leans towards linking the runner into each compiled program as a static library (-buildmode=c-archive; cgo only at release build time, eye itself stays cgo-free), because loading the program with a pure-Go dlopen makes every entity call, step and store access a C-to-Go callback through trampolines. Recommendation: the static library. (6.1 builds a pure-Go loader for @library C functions anyway; that stays right for calling C from the interpreter.)
  2. A package manager, phased. Recommendation: yes, as the analysis proposes. P0 now: path and git dependencies in eye.toml with a local alias as the import root, an eye.lock with content hashes and each dependency's effects, a cache, eye vendor, and minimal version selection; it answers open question 18 (programs sharing Notify). P1: npm's registry as transport, read only by eye's own client, never running scripts, scoped names only, with semver enforced from the API diff. P2: Nix as an optional output (eye gen nix), never a requirement. A registry of our own only after v1.0, if wanted.
  3. New open questions for SPECS, from the analysis: import names for dependencies, whether packages may declare entities and jobs, an effect policy for dependencies, allow lists across packages, and what else belongs in eye.toml. Recommendation: add them as open questions 41 to 45 with P0.
