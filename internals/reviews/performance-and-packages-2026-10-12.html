Performance, the idea, and a package manager, 2026-10-12 ​

An analysis by a reviewing agent of dev at 3b91ced, 2026-10-12. Nothing in the repository was changed. Benchmarks, profiles and three small prototype patches were made in a scratch copy (/tmp/eyebench, not committed). The numbers come from a shared 4-vCPU Linux VM with 15 GB of RAM, using Go 1.27.2, CPython 3.13.16 and Node 22.22. Other sessions were running on the same machine, so repeated runs of one benchmark differed by up to about 30%. Guesses are marked as guesses. What the coordinating session concluded from it is in conclusions-2026-10-12.md, section 6.

Note, added later on 2026-10-12 (ROADMAP 7.8). This page is kept as it was written; some of its numbers are out of date. The quadratic string and map cases (summary items 1 and 2, the quadratic rows of section 1.1) were fixed by R.3 and R.4: 100k string appends now take about 90 ms in the interpreter, and 20k updates over 10k keys about 45 ms, both linear. R.6 made the interpreter's calls and records 2–3× faster, so fib(30) takes about 220–340 ms interpreted, not 750 ms, and the guess of "50–200× over the interpreter" for compiled code (section 1.5) became 10–80× as measured, at 1.1–5.7× Go's time. The current figures, native against Go and the interpreter, are on Benchmarks against Go; the native plan, section 2, says where they come from.

Executive summary ​

  • Plain computation is acceptable for now. The interpreter is 2–9× slower than CPython on loops, calls, records and trees (fib(30): 750 ms against 86 ms). For programs that mostly wait, this does not matter yet.

  • The real problems are slowdowns that grow with the input, not the constant speed. Six were found. Each turns an ordinary program from milliseconds into seconds or minutes:

    1. Building a string with += is quadratic. 100k appends take 18 s; CPython takes 10 ms.
    2. Changing the value of an existing map key copies the whole map. 20k updates on 10k keys take 6–11 s; CPython takes 1.4 ms.
    3. Waking waiting runs is quadratic. 1k runs take 0.33 s and 10k take 25.8 s. This is the scale the "many entities, jobs that mostly wait" pitch promises.
    4. One entity write costs time proportional to the number of entities of that type. It is 0.75 ms with 1k entities and 5.8 ms with 40k, because the store copies the per-type row map on every commit.
    5. eye check takes 9.4 s and allocates 7 GB on a single match over a binary tree. This is in the exhaustiveness checker.
    6. Every store commit copies the event list.

    Fixes for 3, 5 and 6 were prototyped in about 30 lines. The tree check went from 9.4 s to 13 ms. 10k waiting runs went from 25.8 s to 4.2 s. go test ./check ./interp still passed.

  • The memory claims need a qualifier.

    • True: a waiting run holds no goroutine. Resuming takes well under a millisecond, plus one fsync. A looping job's record stays the same size (2.1 KiB) for its whole life.
    • False today: "A waiting job holds no memory at all" (SPECS §1). In eye run, each waiting run costs about 1.5–1.75 KB of RSS plus about 0.6–0.85 KB of journal. The journal and Postgres stores both hold the whole state in RAM. Nothing in the v0.4 plan changes that.

  • The C + Perceus + specialisation plan is sound for computation. Expect roughly 50–200× over the interpreter on CPU-bound code (a guess). It does not fix the slowdowns above, because they live in the Go runner and the store, and v0.4 keeps both. Fix the algorithms in the runner first. Then decide how the runner hosts C code (the analysis leans towards linking the runner into each program as a static library). And let waiting runs leave RAM.

  • The idea holds up. Effects and ! checked by the compiler for durable code, single-writer entities, typed reconciliation, and deterministic tests are a real step past Temporal, Restate and Durable Objects. What users will hit first:

    • the slowdowns above;
    • deploys refused because a job changed under paused runs, with no migration path yet;
    • one runner per store, holding everything in RAM;
    • small papercuts: NonZero division, ?? that works only on Option, record literals that need a named type;
    • no packages, so programs can't share a contract (open question 18).

  • A package manager is feasible and cheap if it reuses existing infrastructure. Recommended order:

    • P0, now: path and git dependencies, an eye.lock with content hashes, and vendoring through the existing modules key. This answers open question 18 at once.
    • P1: npm's registry as transport, used only through eye's own client. It never runs install scripts. Resolution uses minimal version selection (Go's way of choosing versions), not npm's semver ranges, and the publish step diffs the API to enforce semver, as Elm does. Contract packages ship the generated TypeScript in the same tarball.
    • P2: Nix as an optional output (eye gen nix), never a requirement.
    • Later, only if adoption warrants it: a registry of our own.

    The lockfile records the effects each dependency's public API uses, so an update that adds net, ffi or process shows in the diff. No mainstream package manager can do that.

The two quadratic rows are different:

1.3 Hot spots, with file:line (dev 3b91ced) ​

All of these were found with pprof on a small harness that calls check.Program and interp.RunTests.

Slowdowns that grow with the input (fix first):

  1. Exhaustiveness: check/exhaust.go:68 (in missing, from :48). The checker splits a column into constructors even when no row tests that column, which is the case for left and right bound by name. With two recursive fields, the search is exponential up to the depth > 32 cap.
    • Maranget's algorithm uses the default matrix here.
    • Prototype: if every row's head is a wildcard or a binding, recurse on the default matrix. 9.4 s became 13 ms, and go test ./check passed.
  2. The waiting index: interp/store.go:181 (indexed.sleeping). It copies and sorts every waiting run's id, and two call sites run it on every wake:
    • interp/runtime.go:1023 (nextSleeper);
    • interp/runtime.go:410 (wake, which also scans every waiting run to find the few waiting for one event).
    • That makes waking N runs cost O(N² log N).
  3. The store's event list: check/runtime/store.eye:159 (s.events = (s.events |> drop(c.dropEvents)) + c.events). drop makes a list with no spare room, so + copies every retained event on every commit, even an empty one.
    • Prototype of 2 and 3: scan the map without sorting, sort only the runs waiting for that event, and touch events only when the commit changes them. 10k waiting runs went from 25.8 s to 7.0 s to 4.2 s. Runs that touch no entity went from 19.5 s to 3.4 s. go test ./interp passed.
    • A min-heap on wakeAt and an index by event would make each wake O(log N); a guess is under 1 s for 10k.
  4. Entity rows: check/runtime/store.eye:152 plus interp/value.go:261.s.rows |> insert(w.entity, rows |> insert(w.key, row)) replaces a key in the per-type map. Map.with handles a replacement by building a new shelf and running maps.Clone on the index (value.go:187), so every entity write is O(entities of that type).
    • Runs avoid this with buckets of 64 (store.eye:157); rows have no such fix.
  5. Map replace in user code: interp/value.go:261–268. Same cause, so the map-counter idiom is quadratic.
  6. String append: interp/eval.go:995. x + y on Go strings.

Constant factors (the call and loop path):

  • interp/eval.go:108–205: evalArgs, callFunc and bind allocate five slices per call (args, frame slots, bound, paramOf, final), plus the frame. In fib, makeslice and mallocgc are about 30% of CPU.
  • interp/eval.go:207: runBody runs a defer/recover per call, because return is a panic. interp/eval.go:1242: loopTurn runs a defer plus a closure per loop iteration, for break and continue.
  • interp/eval.go:554–563: ref allocates a new &Closure for every reference to a named function, and a new &Variant for every use of a fieldless variant such as Asleep.
  • interp/value.go:564–580: equal falls back to keyOf (value.go:437), which builds a string, for anything but Int, String and Bool. Comparing p == Asleep builds two strings containing the module path; that is 40% of the variant benchmark.
  • interp/value.go:296: Record.with copies both Names and Vals on every field assignment. Names never changes and could be shared.
  • interp/eval.go:954: binary dispatches on operator strings.
  • Int values are int64 in an any. Go boxes values of 256 and above, so arithmetic allocates.

The journal:

  • Each commit is JSON that holds each run record as base64 of JSON, which adds about 33%.
  • The run record includes the 20-step Trail for eye runs (interp/checkpoint.go:492), rewritten in full on every commit. In the looping job measured, each commit was about 2.05 KB; from the decoded record, an estimated four fifths of it is the trail.
  • One run takes three fsync'd commits to reach its first sleep: started as ready, step recorded, then sleeping.

1.5 Does the compilation plan deliver the performance pillars? ​

What it gets right:

  • C through zig cc keeps the toolchain uniform and the bootstrap seed natural.
  • Perceus fits a language with no aliasing, no references and no cycles. Eyelang is closer to the Perceus ideal than Koka or Lean, because mut arguments are checked as unique at the call site.
  • Whole-program specialisation is simple while there are no packages.
  • Saving frames at each ! is the right model for jobs; the interpreter's statement-level checkpoints already proved the idea.

Compiled computation will be fast. Guess: within 2–3× of Go, so 50–200× over the interpreter on CPU-bound code. It also fixes the quadratic string and map cases, provided strings and maps get capacity growth and a unique-owner fast path.

The biggest risks, in order:

  1. The bottleneck that matters is not in the C. Every slowdown that grows with scale in section 1.3 is in the Go runner or in MemoryStore. The pillar "waiting costs no memory" also needs a waiting run's record to leave RAM, and nothing in the plan does that. v0.4 keeps the Go runner and the all-in-RAM store, so the digest would run natively and still cost about 1.5 KB of RAM per waiting run, with quadratic waking.
    • Recommendation: before 7.4, give the runner a timer heap, an index by event, O(1) commits and run records paged out of RAM. In RAM, keep only (id, wakeAt, event), about 40 B (guess), and load the record on wake.
  2. Hosting C from a cgo-free Go runner. Loading the program with dlopen in pure Go (purego style) means every entity call, ! step and store access is a C-to-Go callback through assembly trampolines, with limits on how many callbacks can exist and real cost per call.
    • The alternative is to link the runner into the program as a static library (-buildmode=c-archive, cgo only at release time). That gives a single binary and ordinary cgo calls (tens of ns each). eye itself stays cgo-free.
    • The analysis leans towards the static library, and the decision is blocking 7.6.
  3. Scope. A core runtime in C (big integers, insertion-ordered maps and sets, strings with Offset, formatting, time and zones, fs, process), a Perceus pass and a state-machine split is several thousand lines of subtle code. Guess: 8–15k lines.
    • Prior art moved slowly: Koka and Lean took years, and Roc rewrote its compiler (in Zig) in 2025.
    • Mitigation: run every program's tests on both the interpreter and the compiled build, the way the parser conformance suite does.
  4. Whole-program specialisation against per-module C files and caching. Instances depend on every use, so per-module object caching needs instances emitted by content hash. Once packages exist, specialisation crosses package boundaries, which is fine because packages ship source.
  5. Toolchain weight. The pinned zig 0.17 is 411 MB unpacked, beside a 22 MB eye. Fine for eye build, heavy for someone who only wants eye test; keep it downloaded on demand, as tools/zig does. Zig is pre-1.0, but zig cc is clang underneath and has been stable in practice.
  6. Two representations of a paused run. Interpreter checkpoints are per statement, compiled frames are per !, and both are keyed by code hash. The plan to replay old logs once is right; it needs a test that moves a paused run from the interpreter to compiled code.

Where Eyelang is genuinely new:

  1. Compile-time-checked determinism for durable code, through effect inference and the visible !.
  2. Single-writer entities with value semantics, so nothing is shared mutably.
  3. Exactly-once at the boundary made explicit in types: Uncertain, @reconcile, keys, @fresh.
  4. Contracts that also derive network policy and allowed callers.
  5. Deterministic tests with a test clock and recordings.
  6. A language deliberately shaped for coding agents: canonical formatting, eye fmt writing uses clauses, one way to do each thing.

Where it reinvents:

  • the durable execution engine;
  • the actor runtime;
  • the schema-migration system;
  • cron.

Each is done well, but it is one team carrying what Temporal, Restate and Orleans each spend whole companies on.

What users will hit first, in likely order:

  1. The slowdowns in 1.3. A string built with +=, a word count in a map, a binary tree in a lexer or checker. All three are what an agent writes first.
  2. Papercuts in the first ten minutes, hit while writing the benchmarks: % needs NonZero(Int); ?? works on Option but not Result; 0..n |> toList parses as 0..(n |> toList); let x = { … } needs a named type.
  3. Deploying a changed job with paused runs is refused, with no migrate for resume points and no drain tooling.
  4. One runner per store, all in RAM. Fine for a homelab; the ceiling arrives at about 10^5–10^6 entities or runs (guess, from 0.7–1.75 KB each and the per-type write cost).
  5. No packages. The lab is one program so its parts can share Notify (open question 18).

Part 2: Could Eyelang have its own package manager? ​

2.1 Starting point and constraints ​

  • Modules are directories. import lab.notify names lab/notify under the program root or under a directory listed in eye.toml's modules. So the program root is the module namespace.
  • Open question 5 asks for an eye.lock with hashes "so Nix needs no placeholder hash", and asks whether there should be a registry or git only. Open question 18 asks how separate programs share a contract.
  • Things that already help:
    • modules is a ready-made vendoring hook.
    • tools/zig already pins a binary by version and SHA-256 per platform, which is a package manager in miniature.
    • Public signatures already state their effects; eye fmt writes them.
    • Task 6.4 will generate TypeScript and Go from contracts.
  • Pillars that constrain the design:
    • deterministic tests, so fetching must be hermetic and work offline from a cache;
    • visible costs and effects;
    • agents as users, so commands must be non-interactive with diffable output;
    • a cgo-free single eye binary;
    • "strict but never clumsy".

2.2 The options ​

A. npm's registry as transport (the owner's idea) ​

eye acts as its own small npm client:

  1. Fetch the abbreviated packument (GET https://registry.npmjs.org/@scope/name with Accept: application/vnd.npm.install-v1+json).
  2. Choose a version.
  3. Download the .tgz.
  4. Check dist.integrity (SHA-512).
  5. Extract only .eye, eye.toml, recordings and docs.

It never runs npm and never runs lifecycle scripts.

How each concern works:

  • Publishing: eye pack writes a tarball with a generated package.json (name, version, an "eyelang" field, files). npm publish --provenance from CI with trusted publishing (OIDC) uploads it.
    • npm revoked all classic tokens on 2025-12-09. Write-capable granular tokens are capped at 90 days, and npm login gives 2-hour sessions, so CI with OIDC is the sane path. Leaving publishing to the npm CLI gets provenance (Sigstore) for free.
  • Resolution: npm semver ranges plus a lockfile, or minimal version selection over npm versions. The second treats each ^1.2 as "at least 1.2.0, major 1"; packuments carry each version's dependencies, so this works.
  • Integrity: SHA-512 SRI comes from the registry and is copied into eye.lock. Nix's fetchurl accepts it directly, which removes the placeholder-hash dance that open question 5 worries about.
  • Caching and offline: a content-addressed cache (~/.cache/eyelang/pkg/sha512-…); eye vendor copies dependencies into a directory listed in modules.
  • Private packages:
    • npm private scopes need a paid organisation;
    • GitHub Packages (npm.pkg.github.com) needs authentication even to read;
    • Verdaccio, Artifactory or Nexus self-hosted, all of which speak the same protocol;
    • workable, but more friction than git for a homelab.
  • Security:
    • The worst npm attacks (Shai-Hulud in September 2025, the chalk/debug compromise) spread through install scripts and stolen tokens. An eye that never runs scripts removes the first vector entirely.
    • Typosquatting and account takeover remain. Mitigations: require scoped names (the scope is the publisher's identity, as a domain is for Go), a minimum release age before eye add accepts a new version, and showing the publisher and provenance.
    • Agents add "slopsquatting": a hallucinated package name that an attacker has registered. eye add should refuse unscoped, very new or never-downloaded names without --yes.
  • Policy: npm's Open Source Terms require packages to be "functionally compatible with the npm command-line client" and forbid using the registry "as a general purpose database". An Eyelang tarball with a valid package.json is installable by npm, and a contract package with generated TypeScript is genuinely useful to JavaScript users. The reading here is that this is allowed but at npm's discretion; it is not settled. Keep the source pluggable: eye.lock records URL plus hash, so a mirror can serve the same tarballs.
  • Cost: no hosting. An npm read client is about 1.5k lines of Go (guess), with no node needed to consume packages. Publishing uses the npm CLI in CI.
  • Shared namespace with JavaScript packages: acceptable when names are scoped (@lab/notify). Discovery needs a convention: the "eyelang" field plus a keyword.

The natural fit: contract packages. One npm package @lab/notify holds notify.eye and the TypeScript types and client generated by task 6.4. An Eyelang program depends on it through eye; a TypeScript service depends on it through npm i. Both read the same versioned contract, which is what SPECS §17 promises. Go callers would still want a Go module, which would come from the same build, published to a git tag.

B. Go-modules style: VCS plus checksums plus MVS ​

  • Publishing: push a git tag; there is no registry.
  • Identity: a URL in eye.toml with a local alias, so imports stay short.
  • Resolution: MVS (Russ Cox, 2018). Builds are reproducible without a lockfile, and an upgrade never happens by accident.
  • Integrity: a lockfile of hashes. Go adds sum.golang.org, a transparency log that makes a tag rewrite detectable globally. Running such a log, and a proxy for availability and immutable tags, is real operations work. Without them you get trust on first use per lockfile, which is what most git-based package managers have.
  • Private packages: trivial, through git credentials.
  • Offline: cache or vendor.
  • Security: no scripts. Typosquatting is mostly replaced by trust in URLs.
  • Cost: a git fetch implementation, or shelling out to git. The repository's tarball and codeload URLs also work without git.
  • Since Eyelang packages are source (.eye files), this needs no build infrastructure at all.

C. A registry of our own ​

  • Examples: crates.io, Hex, JSR. JSR also serves its packages through an npm-compatible endpoint, which is a neat hybrid.
  • What it gives: a clean namespace, search, Eyelang-aware documents (eye doc per version), registry-enforced semver, effect manifests and yanking.
  • What it costs: an account system, moderation, abuse handling, malware response and storage, plus an on-call team forever. crates.io and npm both have full-time staff for this.
  • Verdict: not before v1.0 adoption justifies it, and design A and B so that a later registry can mirror them.

D. Nix flakes as the lockfile and build layer ​

  • flake.lock pins inputs.
  • Derivations build hermetically.
  • cache.nixos.org provides zig, Postgres and C libraries for every nixpkgs platform.

What it would buy:

  • Reproducible native dependencies. The C libraries behind @library (zlib, sqlite, libpq) and Postgres for tests, all hermetic and pinned.
  • Dev shells. nix develop gives zig, Postgres and node for a contributor in one step.
  • Hermetic eye build.
  • Binary caches for the native parts.

What it wouldn't buy, and what it costs:

  • Eyelang packages are tiny source trees, so Nix adds nothing for them beyond what a lockfile with hashes gives.
  • Adoption cost: a multi-GB store, a steep learning curve, and slow evaluation.
  • Platforms: macOS works (the Determinate installer). Windows works only through WSL2, and Windows is one of Eyelang's five release targets.
  • Status: upstream Nix still labels flakes experimental, while Determinate Nix markets them as stable. No upstream change by 2026 could be confirmed.
  • The pillars: making Nix a requirement would break "a single binary, developer experience ships with the language".

Verdict: Nix should be optional and come second. eye gen nix turns eye.toml plus eye.lock into a flake:

  • one fetchurl per dependency, using the SRI hash from the lock, so there is no placeholder;
  • zig from the hashes in tools/zig or from nixpkgs;
  • [native] libraries mapped to nixpkgs attributes;
  • a dev shell with Postgres for --store tests.

This is the gomod2nix or importNpmLock pattern. It works only if the lock stores a hash Nix understands:

  • SHA-512 or SHA-256 of the tarball, for registry and URL sources;
  • the NAR SHA-256, for git and directory sources; computing it in Go takes about 200 lines.

Native dependencies without Nix. Since eye ships zig cc, a package can ship the C sources of its @library and a short recipe. eye compiles them with zig for the host, as a shared library the interpreter loads, or for the target, linked into eye build. The result is cached by hash. This is Zig's own package model, and it covers Windows. Nix stays the route for large system libraries (OpenSSL, libpq) and for teams that already use it.

E. Hybrids ​

  • Recommended: sources are pluggable (path, git, npm, later registry); resolution is always MVS; every source is pinned by content hash in eye.lock; Nix is an optional output.
  • The Roc variant: a URL with the content hash inside it, with no lockfile at all. Elegant, but it loses version ranges and upgrades.

2.3 Fit with Eyelang's pillars ​

  • Effects across package boundaries (the distinctive feature). A package's public functions state uses, so eye can compute each dependency's effect footprint and record it in eye.lock:

    toml
    [[package]]
name = "@lab/notify"
version = "1.4.2"
source = "npm"
integrity = "sha512-…"
effects = ["net Notify.send", "net Notify.receipt"]
stateful = false
    • An update that adds ffi, process, fs or a new net operation shows in the lockfile diff that a reviewer or an agent reads.
    • eye.toml can deny effects per dependency (deny = ["ffi", "process"]) and make violations compile errors. This is what LavaMoat or Deno's permissions do for npm, but checked statically and for free.

  • Semver enforced, as Elm does. eye publish diffs the public API against the previous version and refuses a wrong bump. Breaking changes include:

    • a removed or changed signature;
    • an added effect on a pub fn;
    • a new variant on a public type, since every exhaustive match downstream breaks; this is how SPECS §9 wants a new outcome to reach every caller;
    • a contract change that breaks the wire format.

    Elm does this for types; Eyelang can do it for types, effects and contracts.

  • Deterministic tests. eye test never touches the network: the lock plus the cache or vendor/. Recordings shipped in a contract package make its fakes reusable by every consumer.

  • Durable state and upgrades (a hazard unique to Eyelang). A dependency that defines entities or waiting functions puts its code into the program's resume points and stored rows.

    • An eye update that changes such code can make eye run refuse to start (open questions 4 and 23) or need migrations.
    • The lock should mark such packages stateful.
    • eye update should check the new lock against the journal or store and say which paused runs or rows it would strand, before the deploy rather than at start-up.

  • Contracts shared between services in different languages. npm is the natural home for the TypeScript side (6.4) and git tags for Go. One eye publish could produce both from one contract.

  • Agents. Non-interactive eye add, eye update and eye why PKG, with machine-readable output (--json); a lockfile diff that explains itself (versions, hashes, effects); refusal of unverifiable names.

  • The single cgo-free binary. HTTP, tar and gzip, SHA-512, MVS and NAR hashing are all pure Go. tools/zig's download, check and cache code is already the pattern to reuse; zig itself could become [toolchain] zig = "0.17.0" in eye.toml, resolved the same way.

New open questions this raises for SPECS:

  1. Import names for dependencies. Is the eye.toml alias the import root, or does it mirror the package name? Recommended: the alias, for short imports, with identity kept in eye.toml.
  2. May packages declare entities and jobs? Whose store, which migrations, and what happens to resume points on update? Recommended: allow it, flagged stateful, with the update check above.
  3. Effect policy for dependencies. Should there be deny lists, and should ffi in a dependency need explicit consent?
  4. Allow lists across packages. Open question 35's event guard and @allow across packages: a package can't name the program's modules, so eye.toml needs a place to grant them.
  5. Other things for eye.toml. The store (open question 27), model prices (open question 30) and the toolchain pin (zig).

Bottom line: yes. Start with P0 now, since it is small and unblocks open question 18 for the lab. Treat npm strictly as a CDN with integrity hashes, read by eye and never by npm. Use the lock's effect summaries and enforced semver as the feature that sets Eyelang's package manager apart. Keep Nix optional and generated.
