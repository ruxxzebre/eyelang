How Eyelang works ​

This page is a map of the repository for someone who uses Eyelang or wants to change it, and hasn't read the code. It says what each part does, what it takes and gives, and which file to open first. It describes dev as of 2026-10-13. For what is built and what isn't, see What runs today.

A few words first. An entity is a piece of shared state with an owner: its data changes only through its own methods. A job is a function that can wait for days. Each step of a job is a call marked !, whose result is recorded. A run is one execution of a job. A contract describes another service's operations and types. A view is a named query over entities that stays up to date. The glossary has the rest.

1. The pipeline on one screen ​

Every command starts the same way: read the source, check it, and turn it into the resolved IR. From there, a program either runs in the interpreter or is compiled to C.

text
  .eye files + eye.toml
          │
          ▼
  syntax/    lexer → lossless parser → syntax tree ──────────► formatter (eye fmt)
          │
          ▼
  check/     load modules, resolve names, infer types,
          │  check matches and effects
          │  (adds prelude.eye and runtime/store.eye, and std/ modules on import)
          ▼
  ir/        the resolved, typed program                       (eye check --ir)
          │
     ┌────┴───────────────────────┐
     ▼                            ▼
  interp/                      lir/    monomorphic functions in blocks  (eye check --lir)
  reference interpreter           │
  and runtime                     ▼
  (eye run, eye test,          cgen/   C11, plus the runtime written in C
   eye repl)                      │
                                  ▼
                               zig (internal/zig) ──► native binary (eye build)

Three things to know about this picture:

  • The grammar is defined twice. tree-sitter-eyelang/grammar.js is the definition of the syntax. The parser in syntax/ is written by hand, because it gives better error messages. Tree-sitter runs only in tests, as an oracle: the two parsers must build the same tree for every file in the conformance suite.
  • The standard library is Eyelang. check/prelude.eye and the store in check/runtime/store.eye are checked with every program, and the modules in check/std/ (ai, approvals, fs, http, process, random, regex) with each program that imports them.
  • Native code covers the core language only. eye build compiles functions, records, variants, match, loops, closures, strings, collections, traits and tests. Entities, jobs, views and contracts run in the interpreter (eye run) until ROADMAP task 7.6, when the Go runner hosts compiled code. The design is in Compiling Eyelang.

2. The runtime ​

The runtime is the part of interp/ that keeps what a program holds beyond its values: entities, runs, views, the clock and the fakes of other services. The language rules are in the reference's Entities, Jobs and waiting and Views and triggers; the guide's Jobs and waiting explains them with examples.

Transactions. An entity method runs as a transaction: one writer per entity at a time, all or nothing. When a method calls other entities, the whole call tree commits or rolls back together. A served operation is one transaction too. Jobs started and events published inside a transaction happen only if it commits. See txn, callEntity and commit in interp/runtime.go.

Runs and steps. Starting a job makes a run. Each ! call in the job is a step: it runs once, and its result is saved in the run's record. An entity call from a job commits in the same store transaction as the step that records it, so it happens exactly once. A job reads entities only through steps (w.read!(), view.read!()), so a resumed run sees what it saw before.

Checkpoints and replay. At the start of each statement in a job's body, a run that has taken steps since its last checkpoint saves a new one: its variables, the statement it is at, and where each loop around it is. The steps before it are dropped. When a run wakes, it restores the checkpoint and replays only the steps since, each returning its recorded result instead of calling again. So a job that loops for weeks keeps a record the size of its variables. A checkpoint names its statement by a hash of the typed IR, so a run whose code changed under it faults instead of resuming in the wrong place. Open interp/checkpoint.go and interp/jobs.go.

text
  remind("ann") starts                                       run 1
    step 1  notify.send!(…)                 result recorded; entity calls commit with it
            checkpoint: variables and place saved, step 1 dropped
    step 2  next!(answered, within: 3 days)
            the run waits: record on disk, about 140 bytes in memory
    … three days pass, or advance(3 days) in a test …
            wake: record read back, checkpoint restored; step 2 gives None
    step 3  notify.send!(…)                 the reminder, recorded
    end     outcome Completed(…) saved

Waiting. sleep!, next! (an event), approval! (a person), run.join!() and the other waiting calls park the run. A parked run is a handle in memory (its number, job, when it wakes and what event wakes it, about 140 bytes) and a record on disk. See interp/handles.go, sleep in interp/jobs.go, and interp/waits.go for joining runs and locks.

Views and events. When a transaction commits, the runtime updates the views over the entities it changed (updateViews in interp/runtime.go). @on(enters(view)) starts a run for each entity that begins to match, @on(leaves(view)) for each that stops. Events are published on commit, or as a job's step; next! waits for one.

Schedules. @on(daily(07:40, in: zone)), weekdays(…), cron(…) and every(…) start runs on a time zone's clock, with rules for daylight-saving gaps and overlaps (interp/schedule.go). Each firing is saved with the run it starts, so a restart neither repeats nor skips one.

The clock and fakes. Under eye run the runtime's clock follows real time. In a test it starts at 2026-01-01 00:00 UTC, or where with clock(…) puts it, and moves only when the test calls advance(…); runs that wake on the way run in order before advance returns. The playground uses a third kind, a virtual clock (VirtualClock in interp/serve.go) that skips ahead instead of waiting. with fakes(notify, from: "recordings/") answers a contract's calls from recorded exchanges in JSON (interp/fakes.go), checked against the contract when they load. Tests are deterministic in the clock, the store and random numbers; a test reaches the real network only if it calls a service without fakes. The guide's Testing page shows both.

3. The store and the journal ​

Everything a program keeps goes through one interface, Store in interp/store.go: load and save entity rows, run records, events and meta keys, one Commit per transaction.

text
  runtime (interp/runtime.go)
      │  Store interface (interp/store.go)
      ▼
  MemoryStore ─ written in Eyelang: check/runtime/store.eye
      │         an immutable value; each commit is a pure function to the next one
      │         used alone by tests, the REPL and eye run --memory
      │
      ├── wrapped by Journal (interp/journal.go)    ──► DIR/.eye/journal   (eye run's default)
      └── wrapped by Postgres (interp/postgres.go)  ──► --store postgres://…  or $EYE_STORE
  • The in-memory store is written in Eyelang. MemoryStore in check/runtime/store.eye is part of every program and is interpreted like any other code. It doesn't survive a restart on its own.
  • The journal is a file for one machine. It appends each commit, and syncs it to disk before anything outside the runner can see it: before a service call, output, an answered request or a wait. One sync covers every commit since the last. When it opens, and when the file grows past four times the live data, it is rewritten as a snapshot, so it grows with the state, not the history. A line cut short by a crash is dropped.
  • The Postgres store keeps the same state in a database, so it survives the loss of the machine. Each commit is one SQL transaction. One runner writes a store at a time, held by an advisory lock; one database can hold several programs, one per schema.
  • Waiting runs leave memory. Both durable stores keep the record of a run that waits or has ended on disk, and read it back when it wakes.
  • eye runs reads the journal or the database without changing it, so it works while eye run runs. It lists each run's status, what it waits for, and its steps; eye runs DIR 12 3 shows run 12's third step whole. eye approve and eye decline answer an approval! by writing a file to DIR/.eye/inbox, which the runner reads (interp/inbox.go).

The guide's Running in production page covers flags, restarts and stopping.

6. How a language change flows ​

A change to the language touches every stage, in this order. CLAUDE.md is the source for these rules.

#StepFilesCommand
1Write the rule and an example in the spec. A decision gets a row in the decision log (§2); an unsettled idea goes to the open questions (§24).SPECS.md
2Change the grammar. Newlines, braces and strings also need the scanner.tree-sitter-eyelang/grammar.js, src/scanner.ccd tree-sitter-eyelang && tree-sitter test -i 'Name'
3Change the hand-written parser, and the formatter if layout changes.syntax/go test ./syntax -run TestFormat
4Add tests: a valid file per construct, an invalid file per error, and corpus cases.testdata/syntax/valid, testdata/syntax/invalid, tree-sitter-eyelang/test/corpusgo test ./syntax -run TestSyntaxErrors -update, then read the diff of diagnostics.txt
5Regenerate, then check both parsers agree.task generate, task conformance, task fuzz
6Teach the checker; test its messages.check/, tests in check/*_test.gogo test ./check
7Teach the interpreter; add a program whose tests use the feature.interp/, testdata/programs/<area>go run ./cmd/eye test testdata/programs/core, go test ./interp
8Lower it for native code, or make eye build refuse it with a clear error.lir/, cgen/, cgen/testdata, testdata/irgo test ./cgen, go test ./cmd/eye -run TestCheckIR -update
9Editor support.internal/lsp, editors/vscode/syntaxesgo test ./internal/lsp, task vscode
10Docs and bookkeeping: the guide, the status page, ROADMAP.md's "What's next".docs/guide, docs/reference/status.md, ROADMAP.mdtask quick while working, task check before pushing

task quick builds eye, tests the checker, interpreter and parser, then checks and tests the lab's programs in testdata/lab, in seconds. task check runs everything CI runs.

When the language changes under existing code, the fix is a rewrite in eye fix, not a compatibility rule.

8. How work is coordinated ​

Several people and coding agents work on the repository at once.

  • task next says what to do next, from what is true now: the last release and what landed since, ROADMAP.md's "What's next", the open issues, the gaps in What runs today, and what each worktree holds that dev doesn't. Start every session with it.
  • task claim -- WHO PATH… records which paths a session is changing, in the repository's git config, which every worktree shares. task next lists the claims. Leave others' claims alone or ask their owner, and give yours back with task claim -- --release WHO once the work is merged.
  • Worktrees. Each session works in a git worktree of its own, unless it is the one merging into dev. git worktree list shows them.
  • Branches. Development and releases happen on dev; main stays at Eyelang 1 for now. Commits say Closes #N for the ROADMAP task they finish, and the Close issues workflow closes the issue when the commit reaches dev.
  • CI (.github/workflows/ci.yml) runs task check on every push and pull request to dev and main, with a Postgres server and Docker for the tests that need them. A local task check skips those tests, so watch the run after pushing.
